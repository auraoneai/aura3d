# Build a Browser Game with Aura3D

This guide shows the current public root-API path for a browser game route. It
uses `@aura3d/engine`, typed assets generated by the Aura3D CLI, one
`createAuraApp(...)` mount, runtime nodes, input, a kinematic body, and source
evidence.

Aura3D now ships source-level platformer, racing, and falling-block helpers
through the root safe API. Those helpers prove deterministic gameplay rules;
they do not by themselves prove production art direction, game-ready asset
geometry, browser input quality, animation quality, HUD layout, or screenshot
readiness.

## Current Public Pieces

| Need | Public root API today | Boundary |
| --- | --- | --- |
| Mounted route | `createAuraApp(...)` | One Aura app per route. Do not recreate it every frame. |
| Real models | CLI-generated `assets`, then `model(assets.name)` | No string asset ids, invented GLB URLs, `three`, or `GLTFLoader`. |
| Mutable actors | `.runtime(game.runtimeNode("id"))`, `app.nodes.require(id)` | Only marked nodes are mutable at runtime. |
| Frame loop | `app.onFrame(...)`, `app.pause()`, `app.resume()`, `app.step(dt)` | App code owns gameplay decisions. |
| Input | `app.input(...)` or `game.input(...)` | Call `input.update(dt)` once per frame before queries. |
| Movement | `game.kinematicBody(...)`, `game.jumpAssist(...)` | Lightweight deterministic body helpers for custom rules. |
| Collision/combat | `game.collisionWorld(...)`, `game.collider.*`, `game.combatWorld(...)` | Generic collision and focused combat helpers. |
| Genre helpers | `game.platformer(...)`, `game.racing(...)`, `game.fallingBlocks(...)`, `game.fighting(...)` | Source-level gameplay helpers; browser starters still need route tests, game-geometry evidence, screenshots, and visual review. |
| Fighting helper | `game.fighting(...)`, `games.fighting.stagePreset(...)` | Public focused 1v1 kit. |
| Animation control | `AnimationController` / `createAnimationController(...)` | Source-level clip state; visible skinning/morph claims need pixel evidence. |
| HUD/event/accessibility evidence | `game.eventLog(...)`, `game.hud.score(...)`, `game.hud.objective(...)`, `game.hud.eventLog(...)`, `game.accessibility.*` | Route UI still owns DOM layout and rendering. |
| Proof | `app.evidence(...)`, `game.evidence(app, ...)`, screenshots/tests | Source evidence does not replace browser input and pixel checks. |

## Scaffold

For the current public fighting-game starter:

```bash
npx create-aura3d@latest my-fighter --template fighting-game
cd my-fighter
npm run dev
```

The `mini-game` template is the smallest playable platformer-style starter. It
uses `game.platformer(...)`, a typed player asset, keyboard movement, buffered
jump input, scoring, reset, HUD/event evidence, and a browser screenshot test.
Treat it as starter proof, not production game quality.

## Use A Genre Kit First

For platformer, racing, or falling-block routes, start from the public source
kit instead of writing a new route-local rules engine:

```ts
const platformer = game.platformer({
  start: { x: 0, y: 0.35 },
  finish: { x: 12, y: 0.35 },
  platforms: [{ id: "ground", x: -1, y: 0, width: 14, height: 0.35 }],
  collectibles: [{ id: "coin-01", x: 3, y: 1, value: 50 }],
  checkpoints: [{ id: "mid", x: 6, y: 0.35 }],
  hazards: [{ id: "spikes", x: 8, y: 0.35, width: 1, height: 0.2 }]
});

app.onFrame(({ dt }) => {
  const state = platformer.step(dt, {
    moveX: input.axis("moveX"),
    jumpPressed: input.buffered("jump"),
    dashPressed: input.pressed("dash")
  });
  player.setPosition(state.player.x, state.player.y, 0);
});
```

The same rule applies to `game.racing(...)` and `game.fallingBlocks(...)`.
Only write route-local mechanics for behavior the public helper cannot express,
and document that gap as library work.

For public racing or platformer examples, gameplay logic must be bound to the
visible asset geometry. Racing routes need retained topology evidence that
binds the car, checkpoints, camera, and route to the rendered road. Platformer
routes need retained playable-surface evidence that binds the character contact
point, camera, checkpoints, hazards, and finish to the rendered world. Input
tests alone are not enough.

## Add Typed Assets

When the game needs a character, vehicle, arena, prop, or world model, register
a real asset before writing route code.

```bash
npx @aura3d/cli@latest assets add ./assets/fighter.glb --name playerFighter
npx @aura3d/cli@latest assets add ./assets/arena.glb --name arena
```

For catalog-backed work, search or resolve first, then use the generated typed
member:

```bash
npx @aura3d/cli@latest assets search "animated humanoid fighting character" --profile fighting-character --json
npx @aura3d/cli@latest assets resolve "animated humanoid fighting character" --name playerFighter --profile fighting-character
```

Code imports typed assets from `./aura-assets` and uses `model(assets.x)`. Do
not write `model("playerFighter")`, raw `.glb` URLs, `unsafeModelUrl(...)` in
release examples, `new GLTFLoader()`, or `import * as THREE`.

## Minimal Playable Route

```ts
import { createAuraApp, game, lights, model, scene } from "@aura3d/engine";
import { assets } from "./aura-assets";

const app = createAuraApp("#app", {
  scene: scene()
    .add(model(assets.playerFighter).runtime(game.runtimeNode("player", { tags: ["player"] })))
    .add(model(assets.arena).runtime(game.runtimeNode("arena", { tags: ["stage"] })))
    .add(lights.studio())
});

const player = app.nodes.require("player");
const input = app.input({
  actions: {
    left: ["KeyA", "ArrowLeft"],
    right: ["KeyD", "ArrowRight"],
    jump: ["Space"],
    restart: ["KeyR"]
  },
  axes: {
    moveX: { negative: "left", positive: "right" }
  },
  bufferMs: 120
});

const start = [-1.5, 0, 0] as const;
const body = game.kinematicBody({
  id: "player",
  position: start,
  gravity: -18,
  groundY: 0,
  maxSpeed: 4.5,
  jumpVelocity: 7.5,
  coyoteMs: 90,
  jumpBufferMs: 120,
  bounds: { minX: -4, maxX: 4, minY: 0, maxY: 3, minZ: -0.25, maxZ: 0.25 }
});

let score = 0;
let objective = "Reach the right edge";

const events = game.eventLog({ label: "starter route events" });
const hud = game.hud.bindings([
  game.hud.score({ valuePath: "appState.score" }),
  game.hud.objective({ valuePath: "appState.objective" }),
  game.hud.eventLog({ valuePath: "appState.events" })
]);

app.onFrame(({ dt }) => {
  input.update(dt);

  if (input.pressed("restart")) {
    score = 0;
    objective = "Reach the right edge";
    events.push({ type: "restart", label: "Restarted route" });
    body.position = [...start];
    body.velocity = [0, 0, 0];
  }

  body.move(input.axis("moveX"));
  if (input.pressed("jump")) body.requestJump();
  body.consumeJump();

  const state = body.update(dt);
  player.setPosition(state.position[0], state.position[1], state.position[2]);

  if (state.position[0] > 3.5) {
    score += 1;
    objective = "Score again";
    events.push({ type: "score", label: "Scored route loop", value: score });
    body.position = [...start];
    body.velocity = [0, 0, 0];
  }
});
```

This is intentionally small. It proves the route is interactive, but it is not
a reusable platformer kit and it does not prove collisions, level completion,
or animation quality by itself.

## Fighting Runtime Starter

For a focused 1v1 starter, use the current fighting helper:

```ts
import { createAuraApp, game, games, lights, model, scene } from "@aura3d/engine";
import { assets } from "./aura-assets";

const stage = games.fighting.stagePreset("neon-dojo");
const stageIssues = games.fighting.validateStage(stage);

const fighting = game.fighting({
  playerId: "player",
  opponentId: "opponent",
  stage: { width: stage.combatBounds.maxX - stage.combatBounds.minX },
  autoListen: true
});

const app = createAuraApp("#app", {
  scene: stage.nodes
    .reduce((builder, node) => builder.add(node), scene())
    .add(model(assets.playerFighter).runtime(game.runtimeNode("player", { tags: ["fighter"] })))
    .add(model(assets.rivalFighter).runtime(game.runtimeNode("opponent", { tags: ["fighter"] })))
    .add(lights.studio())
});

const player = app.nodes.require("player");
const opponent = app.nodes.require("opponent");

app.onFrame(({ dt }) => {
  const snapshot = fighting.update(dt);
  player.setPosition(...snapshot.player.position);
  opponent.setPosition(...snapshot.opponent.position);
});

const evidence = game.evidence(app, {
  input: fighting.input,
  bodies: [fighting.bodies.player, fighting.bodies.opponent],
  combat: fighting.combat,
  effects: fighting.effects,
  camera: fighting.camera,
  stage: {
    id: stage.id,
    safeZones: true,
    bounds: stage.combatBounds,
    warnings: stageIssues.map((issue) => issue.message)
  }
});
```

## Animation Boundary

Use `AnimationController` or `createAnimationController(...)` for named clips,
restart, crossfade, layers, events, pose snapshots, and runtime-node binding.
Clip names must come from typed asset metadata or an inspection report.

```ts
import { createAnimationController } from "@aura3d/engine";

const animation = createAnimationController({
  id: "player-animation",
  clipRegistry: assets.playerFighter,
  requiredClips: ["Idle", "Run", "LightPunch"],
  suppressRootMotion: true
});

animation.bindRuntimeNode(player, {
  id: "player-animation-binding",
  defaultClipId: "Idle"
});

app.onFrame(({ dt }) => {
  input.update(dt);

  animation.crossFade(Math.abs(input.axis("moveX")) > 0.05 ? "Run" : "Idle", 0.12);
  if (input.buffered("jump", 120)) animation.restart("LightPunch", { restartFromFrameZero: true });
  animation.update(dt);
});
```

This controller state is public source/runtime API. A release-facing claim that
the browser visibly renders skinned GLB animation, morph targets, visemes, or
retargeted locomotion needs screenshot/video evidence with pixel deltas on the
character, not just controller metadata.

## Evidence And Tests

Runtime evidence should be collected after at least one frame:

```ts
app.pause();
app.step(1 / 60);

const evidence = game.evidence(app, {
  input,
  bodies: [body],
  events,
  hud,
  appState: {
    score,
    objective,
    events: events.events().map((event) => event.label)
  },
  assets: {
    typedAssets: Object.keys(assets).length,
    missingAssets: []
  }
});
```

For a route to be called a playable browser game, tests should prove:

- The route imports only public `@aura3d/engine` APIs.
- Primary actors/world assets are typed GLB/glTF assets, not primitive stand-ins.
- Keyboard input visibly changes game state.
- Restart returns the route to a known state.
- At least one score, fail, completion, or round loop changes state.
- Desktop and mobile screenshots are nonblank and show the main subject.
- Racing/platformer routes include retained game-geometry evidence and public
  visual review when they are presented as public examples.
- Any animation, postprocess, WebGPU, PBR, or skinned-character claim has
  matching browser evidence.

## Verify

Use the commands that exist today:

```bash
npx @aura3d/cli@latest assets validate --no-placeholders --require-license
npx @aura3d/cli@latest assets validate-game --profile fighting-character --no-placeholders --require-license
npx @aura3d/cli@latest check-deploy --dist dist
```

Future release gates should add source scanning for raw asset strings,
`GLTFLoader`, `three`, raw GLB URLs, CSS scene effects, primitive-only primary
subjects, and claims that exceed route evidence. Until those CLI gates exist,
reviewers must run equivalent source searches and browser tests manually.
