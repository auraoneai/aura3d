## 1. SSR and glossy materials on the software WebGL2 captures

Question: is SSR or specular IBL dropped or weakened on the SwiftShader path (tier floor, post tiers, SSR roughness cutoff)?

Measured (probe 1, `tests/browser/gu47/e6-probe.spec.ts`, `E6_DIAG` lines, 15 s after ready):

- The SwiftShader floor in `TierResolver.detect` (software renderer -> `low`, which has `ssr: "off"` and
  `environmentSize: 128`) does **not** reach these games. The post tier comes from `resolvePostQualityTier`, which only
  uses the device tier when the `A3D_QR_TIERS_POST` flag is on, and no app turns that flag on, so post resolves to `high`
  (`post.antiAlias.tier: "high"`, `effects.budget.tier: "high"`, `quality.decision: null`). Nothing is weakened by tier on
  the captures. This is the current, deliberate behaviour of the tiers lane (the floor is opt-in); left as is.
- Aura Slam (`top-tennis`): the S3 stage **runs**: `post.stagesRan` contains `S3:ssr-24` (`post.droppedPasses: ["ssr"]`
  is the legacy compiler-bag twin, skipped by design once S3 runs, see lane ec).
- So the trace runs and still shows nothing. Cause: the game authors
  `effects.screenSpaceReflections({ intensity: 0.75, maxDistance: 28, roughness: 0.5, thickness: 0.3 })`
  (`examples/aura-slam/view/lighting.ts:134`), reading `roughness` as a cutoff, as the option doc said ("reflections fade
  out above it; S3 cutoff 0.5"). The S3 trace has no per-pixel roughness (the forward pass writes none; E-D MRT handoff
  still open), so it takes the value as the surface roughness of **every** pixel:
  `roughnessGate = 1 - smoothstep(0.35, 0.5, 0.5) = 0`, and the trace returns zero confidence on every pixel. The stage
  costs its time and adds nothing.
- Same mistake elsewhere: Bunker Zero (`apps/showcase-bunker-zero/src/main.ts:105`, 0.5) and Aura Diamond
  (`apps/showcase-aura-diamond-3d/src/scene.ts:909`, 0.5) are inert too; Aura Hoops (0.45) runs at 26 %, Teleoperator (0.4)
  at 74 %. Aura FC (0.25-0.35), Iron Crown, Dot Dash and Heatsink (default 0) are at full strength.
- Aura Links (`stAuroras`, `mapleHollow`) authors no SSR node; post stages are bloom, GTAO, grade, grain. Its
  "no specular response" is not an engine drop either.

Fix (`220c54e30`), no frame change:

- `AuraScreenSpaceReflectionsOptions.roughness` doc now states the real contract: the frame-wide surface roughness, full
  strength at 0.35 or less, fading to zero at 0.5.
- `renderer.diagnostics(...)` / `app.diagnostics()` warn `SSR_ROUGHNESS_GATED` when the authored value zeroes every
  reflection or scales it down (`ssrRoughnessGate`, `SSR_GATE_START` / `SSR_GATE_END` in
  `packages/engine/src/agent-api/rendererDiagnostics.ts`; the unit test pins them to the shader source).
- Not done, on purpose: switching `roughness` to cutoff semantics. Without a per-pixel roughness channel that would
  mirror every surface (Aura Slam's clay and turf included) and change five games' frames unverified.

Handoff to the game owners (one line each, changes their frame): set the SSR `roughness` to 0.3 in Aura Slam
(`examples/aura-slam/view/lighting.ts:134`), Bunker Zero (`BZ_SSR`) and Aura Diamond, then recapture. Engine follow-up
(E-D): the forward MRT roughness channel, after which `roughness` can become a real cutoff.

## 2. In-source `#define` ignored by the shader preprocessor (g23)

`ShaderPreprocessor` (custom materials and `ShaderLibrary`) resolved `#if` / `#ifdef` against the spec `defines` only. An
in-source `#define WIND_SUN_SHADOW 1` was passed through to GLSL, but the `#ifdef WIND_SUN_SHADOW` block after it had
already been removed by the preprocessor, so The Bellkeeper's Walk never received the sun shadow.

Fix (`c19c90de9`): `#define` and `#undef` lines in an active region now update the working define set (shared across
`#include`s); a `#define` inside an inactive branch is ignored; the lines still reach GLSL. Tests: "honours in-source
#define and #undef in later conditionals" and "sees an in-source #define from an include and ignores #define in an
inactive branch" (both fail on the base).

Frame impact: none today. All 31 built-in shader / variant outputs (default, lean-core and background libraries) are
byte-identical before and after (dumped and compared). No game in the repo has an in-source `#define` read by a later
`#if*` (scan of `examples`, `apps`, `templates`, `src`); Bellkeeper already passes `defines` in the spec (`2de4e0682`), so
its comments in `examples/where-the-wind-wanders-port/{shaders,world}.ts` describing the old behaviour are now stale (left
to the game owner).

## 3. Texture diagnostic stuck at `pending` (g09)

What g09 saw: every luma row carried `texPending=1`, one textured primitive per scene (`fc-pitch` on Munich, the
hidden `cage-w-n` on Lagos; also on Aura Slam, The Siege, Cloud Runner, Roadster Hours and others) "stuck in pending
for the whole session".

Measured:

1. `9b912ecca` added `stage` and `pendingMs` to every `texturedMaterials` row (last step of the textured upgrade:
   `queued`, `start`, `<step> <url>` for each unsettled map load, `decoded`, `done`, `failed`). Bookkeeping only.
2. Probe 1 (`e6p-r1-2`): the stuck row waits inside a map load (`fcTurfRough…jpg` on Munich, 74 s and 111 s;
   `fcConcreteRough…jpg` on Lagos; `net-alpha.png` on Aura Slam), with 79 `none` rows behind it.
3. Probe 2 (`e6p-r3-1`, `tests/browser/gu47/e6-probe2.spec.ts`) timed the engine's load steps on the stuck URL in the
   live page. Munich `fcTurfRough` (121 KB JPG): fetch 14 s, body 26 s, then `createImageBitmap` with the engine's
   options, without either option and with defaults all did **not** settle within 20 s, while `<img>.decode()` of the
   same blob finished (27 s). Aura Slam `net-alpha.png` (**191 bytes**): same, every `createImageBitmap` variant timed
   out, `<img>.decode()` finished. Timers fired about 2x late (20 s caps measured 33-46 s): the page is CPU-starved by
   software rasterisation, and `createImageBitmap` is what starves. The network itself completes (request, response and
   finish events all logged).

The engine defect: the upgrade queue was serial. Only the queue head ever read `pending`; every resource behind it read
`none`, the same as an untextured material, so `texPending` could never exceed 1 and looked "stuck" on one row while the
queue was stalled behind it.

Fix (`762a0ef69`):

- Every resource with texture inputs is marked `pending` (stage `queued`) before any work starts, so the diagnostic
  counts the real queue.
- Upgrades run with concurrency 4 (`PRIMITIVE_TEXTURE_UPGRADE_CONCURRENCY`), so one stalled decode no longer blocks
  every later resource; entries added while the queue runs are picked up by a re-sweep.
- The stage names each unsettled map load as `fetch|body|decode|pixels <url>`.

Verified (`e6p-r4-1`, fixed engine, Munich): `pending: 7, textured: 39` instead of `pending: 1`; the pitch and four cages
in `decode <url>` for all their maps, three cages `queued`. The diagnostic now tells the truth. On this runner the textures
still do not land sooner, because every in-flight decode stalls.

Frame impact (stated as required): final frames are unchanged (same materials). Textures can land sooner on runners
where decodes do complete. `texPending` in luma rows now reports the real queue (7 on FC Munich instead of 1): same
warning in `tools/look-metrics/region-luma.mjs`, larger number.

Not fixed (follow-up for the texture owner): the `createImageBitmap` stall itself. A fallback that decodes via
`HTMLImageElement.decode()` after a timeout would avoid it, but an `<img>` source uploads with different
premultiply / colour-space semantics than the `premultiplyAlpha: "none", colorSpaceConversion: "none"` bitmap. It needs
`UNPACK_*` handling and a pixel check on a GPU and on the software runner, so it is not done in this lane. Until then a
software-runner capture taken while decodes are stalled shows those surfaces untextured, and `texPending > 0` on such a
row is real.

## Phase 7: the `createImageBitmap` stall (handoff 3 follow-up)

Task: fix in the engine the decode stall measured in phase 6, so textured upgrades stop sitting `pending` and captures
show textured surfaces on the loaded software runner. No frame change on a healthy GPU path.

### Fix

- `018e4e572` fix(engine): textured-map decode falls back to an `<img>` when `createImageBitmap` does not settle in 3 s.
  `loadProductionPrimitiveBitmap` (`packages/engine/src/agent-api/compiler/textures.ts`) races
  `createImageBitmap(blob, { premultiplyAlpha: "none", colorSpaceConversion: "none" })` against
  `PRIMITIVE_TEXTURE_DECODE_FALLBACK_MS` (3000). Within the bound nothing changes (same bitmap, same upload). Past it the
  same blob decodes through `<img>.decode()` (`decodeProductionImageFallback`); whichever of the two finishes first is
  used and a late loser is closed. The stage reads `decode-fallback <url>` meanwhile. The result type is
  `ProductionTextureImage` (`ImageBitmap` or an `<img>` with `close()`, which revokes the blob URL); `customTextures.ts`
  and `backgroundImage.ts` take the same loader and type, so custom-material textures and scene backgrounds get the fallback too.
- Why the upload is the same: the WebGL2 source upload (`packages/rendering/src/webgl2/TextureUpload.ts`) already sets
  `UNPACK_PREMULTIPLY_ALPHA_WEBGL = false`, `UNPACK_COLORSPACE_CONVERSION_WEBGL = NONE` and `UNPACK_FLIP_Y_WEBGL =
  texture.flipY` (false) before `texImage2D`. An `<img>` source honours those; an `ImageBitmap` ignores them and carries
  the same three settings from its options. No rendering change was needed.
- `e6512f41d` fix(engine): texture maps read the body once (`response.arrayBuffer()`, decode blob built from those bytes) and
  run the PNG CPU-pixel pass only on PNG bytes (`decodePngTexturePixels` returns nothing for other formats anyway). On the
  runner the old `response.blob()` + `blob.arrayBuffer()` + dynamic import held each map ~40 s in stage `pixels` after the
  fallback decode had landed. Same bytes, same decode, no frame change.
