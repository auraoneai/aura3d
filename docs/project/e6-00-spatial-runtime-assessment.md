## 1. Executive summary

### What exists (public surface in 5.0.3)

- Declarative typed scene (`scene()`, builders, `toJSON()` snapshot) mounted by `createAuraApp`, plus a mutable runtime layer: nodes tagged `.runtime({id})` give handles via `app.nodes.get/require` with setters, a per-node `version`, runtime `add`/`remove` that compile only the subtree (default-on `A3D_QR_COMPILER`), and `app.setScene` (full remount).
- Dense instance writes: `handle.setInstanceMatrices(Float32Array, count, rgba?)` on `instances.<primitive>` nodes, with node-owned storage reused while `count` is unchanged; `instances.mesh` with a three.js-InstancedMesh-style handle; CPU frustum culling inside the forward pass for N >= 512; scatter/merge planners; crowd kit.
- Points: declarative `points()` (static after mount), `geometry.dynamic` / `defineAuraCustomGeometry` with topology `points` driven by `handle.setGeometry` / `handle.updateAttribute`; rendering-level `VertexBuffer` with `writeBytes` and dirty-range upload; `InstanceBuffer`; PLY (public) and PCD/XYZ (internal reachability) parsers.
- Lines and trajectories: `lines.line/loop/segments/fat` with an update path via `setGeometry`/`updateAttribute`; `effects.trail` bound to a node or socket.
- Interaction: public `raycast`/`raycastFirst` over primitive/model/batched nodes (mesh mode with a per-geometry BVH, bounds mode), `createMeshSurfaceQuery`, `bindPointerInteractions`, declarative `interactions.*`, DOM labels (`labels.*`), `text3D`, `@aura3d/addons` `SpatialDOMRenderer`, `@aura3d/controls` (picking, selection, orbit and other controls), app camera controller with rigs and `bindOrbitPointer`.
- Embedding: `@aura3d/react` `AuraCanvas` with hooks (`useAuraApp`, `useAuraFrame`), StrictMode, SSR, hydration, resize, thorough dispose, context-loss surfacing in the engine.
- Determinism and agents: `createFixedStepLoop`, `advance`/`step` headless stepping, `createCountedRng`, input record/replay (`game.inputReplay`, v1/v2 envelopes, driver with `seek`), `runSimulation`, QA hooks, `app.diagnostics()`, scene snapshots as data, `serializeScene`, editor-runtime timeline with `seek`.

### What is missing (verified in code)

1. No typed-array in-place update path on the `points` node (it is compiled once). The workaround (`geometry.dynamic` points) is per-element JS with several O(N) allocations per update and, on WebGPU, needs an unlit material and loses point-size control.
2. `instances.model` silently ignores dense matrix writes; `instances.mesh` rebuilds and reallocates arrays on every compile; instance upload has no dirty range; capacity is fixed at creation.
3. No `app.pick`/projection facade, no points picking, no GPU id pass, instanced picking is a linear CPU scan, `raycast` skips points and lines entirely.
4. No measurement tools, no annotation data model, no coordinate-frame/TF layer, no Z-up camera path for the app camera, no wheel/pan/pinch for the app-bound orbit.
5. React: no ref/imperative handle, no caller canvas, no live-data channel, no picking hook, no context-loss props, window-level game input default, page-global DOM/window state written and never cleared on dispose, no off-screen throttling, no worker mode from React.
6. Engine-wide: full-scene remount on any scene change, O(all nodes) per-frame CPU rebuild with repeated `snapshot()`, always-continuous rendering for any scene with a runtime id, no mutable node API in worker mode.
7. Determinism: no world-state snapshot/restore or seek, input-only replay with a 32-bit default hash, `deterministic: true` is a literal, no scene-snapshot validator or schema, diagnostics `errors[]`/`warnings[]` are untyped strings, no closed author-validate-replay-assert loop.

### Architectural versus application-specific

Architectural (belong in Aura3D, reusable across games, robotics, AV, simulation): the mutable typed-buffer paths (points, instances, lines), WebGPU point rendering design, in-place/dirty-range upload, pick facade and points picking, React handle/live-data/lifecycle hygiene, page-global state, on-demand render, worker mutation channel, determinism contract, state snapshot/seek, scene validation. Application-specific (belongs in AuraOne or an adapter package, not in the engine core): measurement and annotation product tools, sensor/robot file decoders beyond PLY/PCD (LAS/E57/ROS PointCloud2/vendor streams), a TF-style named-frame tree and time-buffered transform store, `ScenarioDocument` modelling robot entities, dashboards and label UX policy, the foreign-app integration itself.

### Honest answer: can Aura3D support this workload today, and what does it take?

Short answer: not as a supported, documented path today, and what would be needed is mostly additive. Whether any given size is workable is unmeasured `[E6-01]`.

- Lidar point clouds at 10-20 Hz (100K to 1M points per frame): the public engine has no typed-array update path for a `points` node. A prototype can be hand-built on `geometry.dynamic` points plus `updateAttribute`, but that path is per-element JavaScript with O(N) temporary allocations, a CPU `refreshBounds` per update, and on WebGPU it needs `material: { unlit: true }` and has no point size control. On WebGPU the point path additionally expands each point to 6 vertices on the CPU every draw and enforces fixed arena budgets that throw rather than degrade (code arithmetic: roughly 155K colored points, 279K uncolored, 116K custom-geometry points per draw before `WEBGPU_POINT_QUAD_BUDGET_EXCEEDED`). Whether the WebGL2 native `gl.POINTS` path (no such budget found) sustains 100K-1M at 10-20 Hz is `[E6-01]`. What it takes: P-01, P-02 (M), possibly P-04, and P-03 for WebGPU.
- Thousands of instances: the best-supported item. `instances.<primitive>` + `setInstanceMatrices` is a public, allocation-free-by-design bulk path. By code reasoning 1K/5K/10K re-posed per frame does not rebuild geometry, materials or buffers; cost per frame is unmeasured `[E6-01]`. `instances.mesh` has per-frame allocation (I-02) and `instances.model` (GLB robots) has no working dense path (I-01).
- Trajectories: `lines.fat` works for static or small updated polylines; per-segment quads (336 B per segment by layout arithmetic), JS tuple rebuild per update and no append mode make large high-rate trajectory sets likely memory/GC-bound `[E6-01]` (I-08, I-09).
- Picking: nodes and instances are pickable by a CPU raycast whose cost is linear in instance count per query `[E6-01]`; points and lines are not pickable through the public raycast; there is no app-level facade (K-01..K-04).
- Annotation: DOM labels exist but scale cliffs are likely in the hundreds `[E6-01]`; `SpatialDOMRenderer` is the foreign-app-friendly overlay but is unwired; measurement and annotation models do not exist (K-05..K-07).
- Embedding in a foreign React app: lifecycle (mount, StrictMode, SSR, dispose, resize) is solid for one instance. Blockers for a foreign host are no ref/handle (R-01), page-global state (R-02), no live-data channel (R-03), and no tested multi-instance behaviour (R-07).

The architectural cure is the same everywhere: keep the declarative, typed scene for structure, and add a mutable typed-buffer path beside it (section 4), reusing the machinery that already exists (`VertexBuffer.writeBytes`, `InstanceBuffer`, handle `version`, `drawRange`). It is additive; the 5.0.3 behaviours stay as defaults.

Items needing the E6-01 benchmark (all cost, memory, latency and scale statements): frame time and GC for 1K/5K/10K instances on all three instance paths; points update cost at 100K/250K/1M on WebGL2 and WebGPU; `bufferSubData` behaviour on in-flight buffers; setScene remount cost and which resources survive it; per-handled-node CPU cost and handle mount cost; pick latency for instances and points; label layer cost at 100/500/2000; JSON key cost for large props; WebGL context count with N canvases; leak return-to-baseline after 50 mount/unmount cycles; WebGL2 point attenuation pixel result; seek/snapshot cost.

## 4. Proposed high-frequency runtime path (design sketch)

Everything below is a sketch for discussion. Names, signatures and shapes are proposals, not committed API. The design is additive: no 5.0.3 behaviour changes by default, and the frozen 5.0.3 release is unaffected.

### 4.1 Principle

Keep the typed declarative scene for structure (what exists, its material, its capacity, its identity) and add a mutable typed-buffer path for bulk data (what the buffers contain this frame). Structure stays diffable, serializable and agent-authorable (`scene().toJSON()`). Bulk data never goes through builders, props, `JSON.stringify`, tuple arrays or `setScene`. The pieces already exist in the codebase and are reused: runtime ids and handles (`app.nodes`), the per-node `version`, `VertexBuffer.writeBytes`/dirty ranges, `InstanceBuffer`, `drawRange`, `setInstanceMatrices`'s node-owned storage, and the compiled-scene `update` hook that runs every frame without recompiling.

### 4.2 Declarative side: capacity and layout, no data

```ts
// Sketch only.
type AuraBufferFormat = "f32x3" | "f32x4" | "u8x4n" | "f32";

interface AuraPointStreamSpec {
  readonly capacity: number;                       // max points; fixed per mount, growth by explicit reserve
  readonly colors?: "u8x4n" | "f32x4";             // omitted = uniform color from the material
  readonly scalar?: boolean;                       // per-point f32 for colormap (P-06, later)
  readonly size?: number;                          // px, with sizeAttenuation as today
  readonly material?: AuraMaterialSpec;            // unlit enforced for the stream path
  readonly bounds?: { min: AuraVec3; max: AuraVec3 }; // hint to avoid per-update bound scans
}

declare const points: {
  (options: AuraPointsOptions): AuraPointsNode;    // existing static path, unchanged
  stream(spec: AuraPointStreamSpec): AuraPointsNode; // node must also carry .runtime({ id })
};

interface AuraInstanceStreamSpec {
  readonly capacity: number;
  readonly colors?: "u8x4n" | "f32x4";
}
// instances.<primitive>(..., { stream: AuraInstanceStreamSpec }) and instances.model(...) declare
// capacity once; matrices stream in through the handle (I-01, I-07).
```

A stream node serializes into the scene snapshot as `{capacity, formats, runtimeId}`: no payload. `compileScene` allocates the GPU buffers once for `capacity` (a `VertexBuffer` with an agreed layout, or an `InstanceBuffer`) and records them in the compiled-scene state beside the existing primitive entries.

### 4.3 Mutable side: handle-owned, typed, bulk

```ts
// Sketch only. Kind-narrowed handle types (U-06): only the matching node kind exposes these.
interface AuraPointStreamHandle extends AuraRuntimeNodeHandle {
  readonly capacity: number;
  /** Copy-in write: one memcpy into the engine-owned CPU buffer, marks the dirty range. */
  write(positions: Float32Array, opts?: { count?: number; offset?: number; colors?: Uint8Array | Float32Array }): void;
  /** Zero-copy write: borrow the engine-owned views, fill them, then commit. Views are invalid after commit. */
  lease(): { positions: Float32Array; colors?: Uint8Array | Float32Array; commit(count: number, dirty?: { start: number; count: number }): void };
  /** Atomic frame swap for 10-20 Hz full replacement (P-04): draws the previous frame until commit. */
  readonly drawCount: number;
}

interface AuraInstanceStreamHandle extends AuraRuntimeNodeHandle {
  readonly capacity: number;
  setMatrices(matrices: Float32Array, count: number, rgba?: Float32Array | Uint8Array, dirty?: { start: number; count: number }): void;
}

// Sensor adapter (adapter package, not engine core):
interface AuraSensorStreamAdapter<Frame> {
  attach(handle: AuraPointStreamHandle): () => void;       // returns detach
  push(frame: Frame): void;                                // decodes straight into lease()/write()
}
```

`write` is the safe default (the caller keeps ownership of its array). `lease` is the zero-copy option for decoders that can write into engine memory (PCD binary, PointCloud2 layouts, WebSocket frames). Updates remain valid from any task between frames.

### 4.4 Lifecycle and ownership rules

1. Identity: the declarative node defines kind, capacity and format; the runtime id is the only handle key. `app.nodes.require(id)` returns a stream handle after mount.
2. Ownership: the engine owns the CPU mirror and GPU buffers for the node; the caller owns any array passed to `write`, and engine code never retains it after the call returns. Leased views belong to the engine and are invalid after `commit` or after the next `lease`.
3. Commit boundary: writes are staged; the frame loop applies the staged commit once, at the start of the frame, before `updateCompiledScene`. A write that lands mid-frame is applied next frame and never tears the frame being built. The handle `version` bumps once per commit, not per element.
4. Capacity: fixed per mount (matches today's instances rule). Exceeding it throws a typed error (as `INSTANCE_CAPACITY_EXCEEDED` does today). Explicit `reserve(n)` may grow by doubling, which reallocates and is documented as a rare, costly call.
5. Count and visibility: count shrink and grow are `drawRange` changes, not reallocations. A count of zero hides the node while keeping capacity.
6. Bounds: either the declared hint, an engine-computed bound refreshed lazily (on the next cull-relevant read), or an explicit `setBounds`. Stale bounds are a correctness risk (a visible cloud culled), so default is lazy-exact and the hint is opt-in.
7. Remount: `setScene` and runtime `remove` dispose the stream; held handles are invalidated as all handles are today. Staged but uncommitted data is discarded. Context loss: the CPU mirror re-uploads on restore (the existing `VertexBuffer.upload` generation check is the mechanism).
8. Worker mode: unsupported until U-05 adds a transferable channel; calling `write` on a worker app throws the existing "unsupported" style error.

### 4.5 Interaction with `compileScene` and the frame loop

- Mount: `compileScene` sees a stream node, allocates one buffer set for `capacity`, creates one `RenderItem` (one draw per node), and registers a handler `update` that consumes the staged commit (apply dirty range via `writeBytes`/`markDirtyRange`, set `drawRange.count`, refresh bounds if requested).
- Per frame: `updateCompiledScene` already iterates handled nodes and calls `handler.update` (points, line, batched, sprite handlers today). The stream handler's `update` is O(dirty bytes) and allocation-free; it must not call `snapshot()`. The existing `reuseRenderItems` identity cache keeps the item identity when nothing changed.
- Frame scheduling: with U-04 a commit calls `invalidate()` so an on-demand app renders exactly once per commit; in continuous mode nothing changes.
- Picking: the stream's typed positions are the source for K-03; the spatial index is built lazily on first query after a commit, never per commit.
- React (R-01, R-03): `AuraCanvas` exposes a handle; a hook such as `useAuraStream(id)` returns the stream handle; React never renders per sample. Scene props carry capacity and layout only.
- Determinism: a commit is a timestamped input to the frame (`advance`), so replay drives commits at fixed steps and a digest can hash committed buffers (D-04).

### 4.6 Risks

- Surface sprawl: three bulk-write idioms already exist (`setInstanceMatrices`, `setInstanceTransforms`, `instances.mesh` setters). The sketch must replace, not add (U-06): one documented contract, old members kept as aliases.
- Tearing and ownership bugs if `lease` is misused; mitigated by commit-boundary application and invalidation of views.
- Stale bounds culling visible data; mitigated by lazy-exact default.
- WebGPU: until P-03 the stream node still pays the per-draw 6x CPU expansion and arena budgets; the stream API can ship first on WebGL2 and degrade explicitly on WebGPU (typed error at mount when capacity exceeds the arena budget).
- Interactions with always-rebuild volatile nodes and the item cache (U-03); stream nodes are not volatile, which the cache must treat as unchanged unless the version moved.
- Gating: new exports touch `aura.exports.json` and the API-surface gates; claims about speed must wait for E6-01 numbers.

### 6.2 Recommended sequencing for 5.1

Scope discipline: 5.1 is a minor, additive release. It contains reusable engine capabilities useful beyond AuraOne (games, robotics, AV, simulation viewers). AuraOne application work (measurement/annotation product tools, sensor decoders, TF store, dashboards, the foreign-app integration) stays outside the engine, in an adapter package or in AuraOne. Frozen 5.0.3 is unaffected: every change is opt-in or a pure bug fix behind existing tests; default behaviours and golden frames stay identical.

Order (each step independently shippable; steps in the same stage can run in parallel lanes because they touch different files):

Stage 0, evidence first (about 2 engineer-weeks, parallel with stage 1 design):
- U-01 benchmark baseline, including the three.js protocol runs for the same scenarios. Its numbers decide the evidence-gated items (P-03, P-04, I-03, I-04, K-02, K-04, K-05, U-02, U-03).
- D-10 high-frequency determinism suite scaffolding if capacity allows.

Stage 1, unblockers and correctness (small, low risk, can start immediately):
- I-01 phase 1 (throw instead of silently ignoring), I-05 types (dead option types), I-07 capacity option, P-05 WebGL2 point size correctness, P-08 docs, R-11, R-05, R-06, R-09, D-03 (tier table and the two `Math.random` sites), D-02 counter and never-drop, U-04 on-demand render.

Stage 2, the typed-buffer path (core of 5.1):
- U-06 handle contract (kind-narrowed types, one documented bulk write), P-01 typed `points()`, P-02 in-place points update, I-01 phase 2 (model dense path), I-02 `instances.mesh` allocation, I-08 line fast path and append.
- Ship the stream API of section 4 on WebGL2 first; WebGPU keeps its existing path and fails clearly at mount when over budget until P-03.

Stage 3, interaction and embedding (parallel to stage 2 once K-01 and R-01 land):
- R-01 handle, R-02 page-global state, R-03 live-data hook (needs stage 2), K-01 pick/projection facade, R-04 `onPick`, K-03 CPU point picking (needs P-02), K-06 overlay adapter, K-08 app-camera orbit with Z-up, K-09 `getWorldMatrix` plus Z-up convention note, R-07 off-screen observer and multi-instance spec, R-10 leak spec, D-05 scene snapshot validator.
- K-02 instanced picking only if E6-01 shows pick latency is a problem.

After 5.1 (evidence-gated or large): P-03 WebGPU points, P-04 stream ring, P-06/P-07, I-03/I-04/I-06/I-09/I-10, K-04 GPU picking, K-05 label scale, K-10, U-02, U-03, U-05 and R-12 worker mutation path, R-08, D-01/D-04/D-07/D-08/D-09 replay and agent loop. Adapter/AuraOne track: P-09 decoders, K-07 measurement/annotation, K-09 TF store, D-06 scenario document.

Rough size of the 5.1 candidate set, from the register's estimates (work estimates, not commitments): Stage 0 about 2 engineer-weeks; Stage 1 about 9-11; Stage 2 about 10-14; Stage 3 about 22-27 (K-03 alone is 4-6). Parallelised across lanes this is the scale of one minor release, but the total depends on U-01 and on how much of Stage 3 the owner schedules.

### 6.3 What not to do in 5.1

- Do not add per-point or per-instance diagnostics to `diagnostics()` (bounded by design).
- Do not unify `@aura3d/controls` and the engine camera stacks wholesale (K-08 is an adapter plus an up-axis option).
- Do not change the global coordinate convention (Y-up) engine-wide; document a root-group rotation first.
- Do not write any speed or comparison claim from this assessment; claims wait for E6-01 evidence and the labels in `docs/agents/claims-and-boundaries.md`.
