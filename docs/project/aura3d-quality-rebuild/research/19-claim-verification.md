# 19 — Adversarial verification of load-bearing claims

Two independent skeptics per claim (code-trace lens, alternate-path lens). Static code reading only.

## C1. verdicts: partially-true, partially-true
**Claim:** Adding lights.ambient() with no environments.* node makes the production bridge set environmentMapIntensity and environmentMapSpecularIntensity to 0 with no env texture (packages/engine/src/agent-api/index.ts ~12686-12707), so the scene has zero image-based lighting; ~20 of the 18 games + other showcases do this.

**Skeptic 1 (partially-true):** The code part of the claim holds. In packages/engine/src/agent-api/index.ts, createProductionRuntimeEnvironment (defined at line 12628, called once at line 13613) works in this order. First it looks for an authored `kind: "environment"` node (lines 12638-12692). If there is none, it collects ambient lights with intensity > 0 (line 12693). If there are any, it returns preset "authored-ambient" with `lighting: { color, intensity, environmentMapIntensity: 0, environmentMapSpecularIntensity: 0 }` (lines 12700-12705). No proceduralMap and no hdriUrl are set, so the HDRI upgrade at 13631 never runs. The scene gets only a flat, weighted-average ambient term with zero environment-map diffuse or specular, meaning no image-based lighting (IBL). If there are no ambient lights either, it falls back to a generated preset (gameplay, studio, etc.) with IBL (lines 12707-12720). So adding lights.ambient() without an environments.* node turns off the IBL fallback the scene would otherwise get.

The count is wrong as written: "~20 of the 18 games" contradicts itself. My filename-level tally found lights.ambient( with no environments.* call in the src of 23 showcase apps (excluding art-review, art-candidates and scripts): asset-audition, aurora-lander, bank-shot, blockfall-reactor, courier-rush, deep-recovery, digital-twin-ops, gallery-shift, gravity-post, mech-hangar, meshy-relic-pilot, neon-swarm, orbital-defense, patrol-wing, pulse-tunnel, rooftop-buckets, skyline-runner, smart-city-control, vault-breakers, webgpu-particle-lab, plus aura-clash-showcase. It is also true for templates/racing-starter, templates/falling-blocks-starter and examples/neon-corridor-strike. Four showcases use both and therefore keep IBL: cinematic-architecture, product-configurator, siege-golf and turbo-drift-circuit.

*Counter-evidence:* There is no counter-evidence on the code path: the zero environment-map intensities are hard-coded at lines 12704-12705. The weak points are the number and its framing. "~20 of 18" cannot be literally true. Also, my tally checks files, not node graphs: an app might add an environment node through a helper that doesn't call environments.*(...) or write a literal `kind: "environment"`. The 4 apps that do author an environment node take the environment branch and get IBL.

*Scope:* This applies only to the createAuraApp production bridge (the single call site at index.ts:13613). Precedence matters: any authored environment node wins, even if ambient lights are also present. Ambient lights with intensity 0 are filtered out, so they fall through to the generated-preset IBL. The authored-ambient result has no hdriUrl, so the B3 HDRI upgrade never replaces it. I did not check which apps make up the canonical "18 games" list (the docs mention 18 but I didn't compare against it), whether sky.dayNight or prefabs emit environment nodes indirectly, or any runtime pixels.

**Skeptic 2 (partially-true):** The mechanism is confirmed. In createProductionRuntimeEnvironment (packages/engine/src/agent-api/index.ts:12628), an authored environment node wins at :12638. If there is none, the ambient branch at :12693-12707 runs whenever any lights.ambient node has intensity > 0. It returns lighting { color, intensity, environmentMapIntensity: 0, environmentMapSpecularIntensity: 0 } with no proceduralMap or HDRI. In production-runtime/index.ts:1455 and :1566, `iblIntensity = environmentMapIntensity ?? pipeline.intensity`, so the explicit 0 is kept and IBL is fully off. The ambient color and intensity survive only as flat irradiance with no specular. The same code applies the HDRI upgrade only when an environment node exists (:13613-13650). An app that adds no ambient and no environment instead gets the generated HDR fallback with an environment map (:12709-12722). So adding ambient light actively removes IBL the app would otherwise have had by default. The count in the claim is wrong. Of the 28 apps (aura-clash plus 27 showcase-*), 21 add a nonzero lights.ambient and no environments.* node: asset-audition, aurora-lander, bank-shot, blockfall-reactor, courier-rush, deep-recovery, digital-twin-ops, gallery-shift, gravity-post, mech-hangar, meshy-relic-pilot, neon-swarm, orbital-defense, patrol-wing, pulse-tunnel, rooftop-buckets, skyline-runner, smart-city-control, vault-breakers, webgpu-particle-lab, plus world-war-x-showcase (rendering/GameLighting.ts:16). Among the games, about 15-16 of 18 hit the path, not "~20 of 18".

*Counter-evidence:* Aura Clash does not hit the path, even though it has a lights.ambient call. createAuraClashLightRig (apps/aura-clash-showcase/src/rendering/GameLighting.ts:176) is documented as "not the rig the playable route renders with". The root createAuraApp scene (AuraClashArenaApp.ts:1496) adds only lights.spot, so it falls through to the generated "gameplay" HDR fallback, which has an environment map. The fighters and arena go through a separate production-runtime compatibility path with renderPreset.environmentLighting (:1405). Three showcases add an environment node, so the ambient branch is skipped for them: siege-golf (environments.studio, main.ts:838), turbo-drift-circuit (environments.studio, main.ts:3002), and cinematic-architecture and product-configurator (studio/nightCinematic and productHero). data-galaxy and material-asset-inspector have no ambient and use the fallback or kit environments. Game kits (game.platformer, racing, fallingBlocks, fighting) and sceneKits.cityBlock add no environment node (cityBlock uses lights.studio), so nothing rescues the ambient-only apps. No later override was found: the HDRI upgrade needs an environment node, and iblIntensity keeps the explicit 0.

*Scope:* The claim applies only to scenes rendered through the root createAuraApp production bridge. Advanced-runtime or compatibility render paths that pass their own environmentLighting are not affected; Aura Clash is the main example. Conditional scenes are possible: for siege-golf and turbo-drift I did not check that the environment node and the ambient node always sit in the same snapshot, and if one mode drops the environment node, that mode would hit the path. "Zero IBL" is accurate, but "zero ambient" is not, because the flat ambient color and intensity still apply. The exact line range is 12693-12707 (ambient branch) and 12706 (the zeros), close to the cited ~12686-12707; lines 12686-12689 are the environment-node branch, which multiplies the bundle's environment-map intensities rather than zeroing them. All checks were static rg/sed reads; no runtime or pixel verification was done.

## C2. verdicts: confirmed, confirmed
**Claim:** The default quality profile safe-basic defines pixelRatio 1 and that value wins over window.devicePixelRatio (agent-api/index.ts ~4256, ~11129), so retina displays render at 1x unless the app overrides pixelRatio.

**Skeptic 1 (confirmed):** The claim holds in the current checkout. In packages/engine/src/agent-api/index.ts, the "safe-basic" quality profile sets pixelRatio: 1 (line 4256). resolveRendererQualityProfile falls back to "safe-basic" when qualityProfile is not set (line 4312), and normalizeCreateAppRendererOptions uses that function (line 4318). createAuraApp (line 11129) sizes the canvas with `configureCanvas(canvas, options.pixelRatio ?? rendererSelection.profile.pixelRatio ?? devicePixelRatioSafe(), ...)` (line 11133). The production render path calculates pixelRatio with the same expression (line 12280) and reuses it in resizeRenderer (lines 12301-12302). AuraRendererQualityProfile.pixelRatio is a required number (line 1772), so `profile.pixelRatio` is never null or undefined. That makes the devicePixelRatioSafe() fallback (lines 18699-18700, which clamps window.devicePixelRatio to [1,2]) unreachable on these paths. The default backing store is therefore 1x CSS size on retina displays, scaled by performanceQuality.resolutionScale on resize. Exceptions: the app sets options.pixelRatio, or chooses renderer.qualityProfile "production" or "cinematic" (both pixelRatio 1.5, still a fixed value that ignores the real device ratio). "experimental-webgpu" is also 1.

*Counter-evidence:* I found none on these code paths. devicePixelRatioSafe() is the third operand of `??`, but the second operand (profile.pixelRatio) is always a finite number from the static profile table, so window.devicePixelRatio is never consulted on either path. Other packages do read the real device ratio: packages/rendering/src/Renderer.ts:508 (options.devicePixelRatio ?? globalThis.devicePixelRatio) and :1794, and packages/lean/src/base.ts:495. These belong to the lower-level renderer and lean entry points, not to the agent-api createAuraApp canvas sizing. I did not trace whether createProductionSceneRenderer later calls Renderer.resize with the real device ratio. On the root resize path, resizeRenderer sets canvas.width/height itself and calls renderer.resize(width, height) with explicit pixel sizes.

*Scope:* This affects every createAuraApp consumer (games, templates) that does not pass pixelRatio or a non-default qualityProfile: they render at 1x on high-DPI screens. Even with "production" or "cinematic" the ratio is fixed at 1.5, so a 2x or 3x display is never matched natively. The 320x220 minimum backing size in configureCanvas and resizeRenderer is a separate floor. The resize path multiplies by resolutionScale. The line references in the claim (~4256, ~11129) are accurate: the profile is at 4249-4263, the selection at 11129, and the use at 11133. This was a read-only code trace; I ran nothing at runtime.

**Skeptic 2 (confirmed):** Confirmed, with two refinements. In packages/engine/src/agent-api/index.ts, the default profile is safe-basic: resolveRendererQualityProfile falls back to it at line 4312, and it sets pixelRatio: 1 at line 4256. Both places that size the backing store resolve the ratio as `options.pixelRatio ?? rendererSelection.profile.pixelRatio ?? devicePixelRatioSafe()`: configureCanvas at line 11133 and the production resizeRenderer at lines 12280 and 12301-12302. All four profiles define a numeric pixelRatio: safe-basic 1, production 1.5, cinematic 1.5, experimental-webgpu 1 (lines 4256, 4271, 4286, 4301). So devicePixelRatioSafe() (line 18699, which caps DPR to the range 1-2) can never be reached through createAuraApp or createGameApp. createGameApp (line 11818) just forwards its options to createAuraApp. Nowhere else in packages/engine/src reads window.devicePixelRatio. Refinement 1: no profile ever follows the device's DPR. Without an explicit override, the result is a fixed 1x for safe-basic and a fixed 1.5x for the production profile, whatever the display. Refinement 2: getRootPerformanceQuality().resolutionScale can only multiply that fixed ratio further. It never brings DPR back in.

*Counter-evidence:* Some apps get around the default by passing their own pixelRatio or choosing the production profile:
- Device-DPR-aware overrides: aura-clash-showcase (AuraClashArenaApp.ts:1522, min(DPR, 1.75) in normal play, production profile), showcase-rooftop-buckets (main.ts:738, min(DPR, 1.75)), product-configurator (min(DPR, 1.5), production profile), material-asset-inspector (min(DPR, 1.5)), cinematic-architecture (min(DPR, 1.45)), asset-audition and digital-twin-ops (min(DPR, 1.35)), webgpu-particle-lab (min(DPR, 1.2)).
- Production profile with no override, so a fixed 1.5x: showcase-mech-hangar (main.ts:705), showcase-vault-breakers (main.ts:392).
- Fixed values that are at or below 1x anyway: skyline-runner (main.ts:1879, 0.7 on safe-basic), data-galaxy (1), smart-city-control (main.ts:383, 1 or 0.25 with the production profile).
None of these is an engine path that defeats the claim. They are the app overrides the claim already allows for.

*Scope:* Games that do hit the default 1x path (no pixelRatio and no qualityProfile in the createAuraApp/createGameApp call in src/main.ts): showcase-aurora-lander, bank-shot, blockfall-reactor, courier-rush, deep-recovery, gallery-shift, gravity-post, meshy-relic-pilot, neon-swarm, orbital-defense, patrol-wing, pulse-tunnel, siege-golf, and turbo-drift-circuit. Turbo-drift-circuit sets pixelRatio 1 only in visual capture (main.ts:2988). Its comment says public gameplay "keeps its renderer-selected device pixel ratio", but that ratio is actually the safe-basic 1. So about 13-14 games run at 1x on retina, and skyline-runner deliberately goes below that at 0.7. aura-clash-showcase and rooftop-buckets follow device DPR up to 1.75. mech-hangar and vault-breakers get a fixed 1.5. The default path is reached through createGameApp (index.ts:11818-11820), which spreads its options into createAuraApp. I did not check which app list makes up the audit's "18 games" (showcase-index lists 23 showcase-* routes), and I did not verify any runtime canvas sizes in a browser.

## C3. verdicts: confirmed, partially-true
**Claim:** model(asset, { material: { color } }) sets replaceSurfaceTextures:true, which disables base color and metal-rough textures on every material of the GLB, forces roughness ~0.38/metallic ~0.16 and adds emissive = base color at ~0.28 (agent-api index.ts ~13567-13580, production-runtime/TypedGLBActor.ts ~476-510).

**Skeptic 1 (confirmed):** The claim is true for the current checkout, with some qualifications. In packages/engine/src/agent-api/index.ts:13567-13580, createProductionRuntimeSceneRenderer passes tint: { baseColor: colorToLinearRgba(color), replaceSurfaceTextures: true, ... } to createTypedGLBActor whenever node.material?.color is truthy. It does this unconditionally; callers cannot opt out. TypedGLBActor.ts:207-208 applies the tint through tintTypedGLBActorMaterials (lines 477-482), which loops over every material in pipeline.resources.materialLibrary. applyMaterialTint (lines 484-514) does the following:
- Sets u_baseColor and u_baseColorFactor to the tint color (lines 496-497).
- Sets u_baseColorTextureEnabled=0 and u_metallicRoughnessTextureEnabled=0 (lines 498-501). The PBR shaders read both flags (packages/rendering/src/ShaderLibrary.ts:925-929), so the albedo and MR maps really are ignored.
- Sets emissive to tint.emissiveColor, falling back to the base color RGB (line 478), with u_emissiveStrength = tint.emissiveStrength ?? 0.28 (lines 502-505).
- Sets u_roughness = tint.roughness ?? 0.38 and u_metallic = tint.metallic ?? 0.16 (lines 506-507).

*Counter-evidence:* "Forces" overstates it. The values 0.38, 0.16 and 0.28, and emissive = base color, are only defaults. The bridge forwards material.roughness, material.metallic/metalness, material.emissive and material.emissiveIntensity when they are set (index.ts:13571-13576), and those override the defaults.

Materials whose name matches /joint/i are handled differently:
- Base color is darkened to about 0.22-0.28x.
- Emissive is scaled by 0.28 and its strength is capped at 0.08.
- Roughness is at least 0.72 and metallic at most 0.08.

The normal, occlusion and emissive texture flags are not touched, so those maps still apply. The emissive texture is multiplied by the tint glow (ShaderLibrary.ts:931).

*Scope:* This only affects model nodes on the production-runtime path, where createAssetProvenance(node.asset).source === "typed-aura-assets-manifest" (index.ts:13547-13549, reached from index.ts:12544). Other model paths were not traced.

The tint is triggered by node.material.color alone. Setting emissive or roughness without a color does not tint. replaceSurfaceTextures: true is hard-coded at index.ts:13570, and repo-wide that is the only place it is set.

Line references: the claim's "~476-510" range is accurate. The function starts at 477 and the relevant logic runs to 514.

**Skeptic 2 (partially-true):** Confirmed mechanism: in packages/engine/src/agent-api/index.ts:13568-13580, any typed-manifest GLB model node with a truthy node.material.color gets tint { baseColor, replaceSurfaceTextures: true, ... }. That tint is passed to createTypedGLBActor, which calls setTint (TypedGLBActor.ts:207-208), then tintTypedGLBActorMaterials (477-482). For every material in pipeline.resources.materialLibrary, applyMaterialTint (484-515) sets u_baseColorTextureEnabled=0 and u_metallicRoughnessTextureEnabled=0 (498-501). These are real shader/resource uniforms (packages/assets/src/GLTFRenderResources.ts:257,259; rendering/src/ShaderLibrary.ts:614). Normal, occlusion and emissive textures are not disabled.

What the claim overstates: roughness 0.38, metallic 0.16, emissive = base color and emissiveStrength 0.28 are only fallbacks, applied when the spec leaves out roughness, metallic, emissive or emissiveIntensity (index.ts:13572-13577; TypedGLBActor.ts:478, 504-507). The games build specs with material.pbr (index.ts:2415-2421), which always fills roughness 0.55 and metallic 0, so the 0.38/0.16 defaults never apply through that helper. The games also mostly pass explicit values. Gravity Post's dock gate (apps/showcase-gravity-post/src/main.ts:492-499) uses roughness 0.26, metallic 0.42, emissive #22d3ee at 0.18. Courier traffic cars (apps/showcase-courier-rush/src/main.ts:391-398) use roughness 0.26, metallic 0.48 and clearcoat, but set no emissive, so they get emissive = base color at 0.28. Siege Golf's crate (apps/showcase-siege-golf/src/main.ts:64-70, 329) uses roughness 0.46, metallic 0.08, and also gets the base-color emissive at 0.28.

Materials whose name matches /joint/i are handled separately (TypedGLBActor.ts:490-507): darkened color, roughness of at least 0.72, metallic of at most 0.08, emissive scaled by 0.28 and capped at strength 0.08. Their textures are still disabled.

material.pbr() always injects color "#d7dee8", so passing material.pbr({...}) with no color still triggers the texture wipe.

*Counter-evidence:* There is no option that turns replaceSurfaceTextures off: it is hardcoded true at index.ts:13570, and nothing calls setTint later in a way that would restore textures. All renderer quality profiles default to rendererMode "production" (index.ts:4253-4298). The only routes around it are non-typed or unsafe models and a production-bridge failure, which falls back to createWebGLSceneRenderer (index.ts:12529-12548); the games normally do neither. Aura Clash (apps/aura-clash-showcase/src/playable/AuraClashArenaApp.ts:761-793) calls createTypedGLBActor directly with no tint, so the path never touches it. The roughness/metallic numbers in the claim are not what games actually get: material.pbr's own defaults (0.55/0) or the game's explicit values override them.

*Scope:* The texture-disable part is confirmed for every showcase game that passes a material into model() on a typed GLB. Confirmed directly: gravity-post (dock gate), courier-rush (traffic sedan/hatch; city.ts also has a hit), siege-golf (siegeWoodenCrate only, and only in the physics visuals). A loose multiline rg also flags model(...material...) in asset-audition, data-galaxy, deep-recovery, material-asset-inspector, product-configurator, aurora-lander, neon-swarm, patrol-wing, webgpu-particle-lab, turbo-drift-circuit, skyline-runner and pulse-tunnel art-review files; those were not checked one by one. aura-clash-showcase is not affected. The emissive = base color at 0.28 effect only applies to specs without an explicit emissive or emissiveIntensity (courier cars and the siege crate, yes; the gravity gate, no). The 0.38/0.16 roughness/metallic defaults effectively never apply when specs come from material.pbr/material.physical. Nothing was checked at runtime or visually; this is a read-only trace of the code.

## C4. verdicts: confirmed, confirmed
**Claim:** The shadow DepthPass uses a single position-only MVP depth shader that ignores skinning, instancing/static batching instanceTransforms, morph targets and alpha cutout (packages/rendering/src/DepthPass.ts ~59-84, ShaderLibraryCore.ts ~784-805), so animated characters cast bind-pose shadows and batched/instanced casters cast wrong or no shadows.

**Skeptic 1 (confirmed):** Confirmed in the current checkout. DepthPass.drawCaster (packages/rendering/src/DepthPass.ts:59-87) reads only caster.geometry, drawRange, modelMatrix and the light viewProjection. It sets a single uniform, u_modelViewProjection = VP * modelMatrix, and issues one non-instanced device.draw using the DepthMaterial (requiredAttributes ["a_position"] only, DepthPass.ts:15-27). It never reads RenderItem.skinning, morphTargets/morphWeights, instanceTransforms/instanceColors/instanceAttributes or any material alpha/cutoff, even though all of these exist on RenderItem (ForwardPass.ts:24-48). The shader is registerLeanDepthShader (ShaderLibraryCore.ts:784-805). Its vertex shader is `gl_Position = u_modelViewProjection * vec4(a_position, 1.0)` with only a_position. Its fragment shader writes gl_FragCoord.z unconditionally, with no texture sampling and no discard. Nothing registers any other variant under "aura3d/depth"; the only registrations are ShaderLibraryCore.ts:899 and ShaderLibrary.ts:3325.

What this does to each kind of caster:
(a) Skinned characters cast bind-pose shadows. ForwardPass skins on the GPU through applySkinningUniforms (ForwardPass.ts:437, 1942), and the depth pass never does this.
(b) Morph targets are ignored.
(c) Static-batched casters cast wrong shadows. batchStaticRenderItems (SceneOptimization.ts ~212-216) emits items with modelMatrix = identity and per-copy matrices in instanceTransforms. The depth pass therefore draws one copy of the geometry at the identity/origin transform instead of N copies. These batched items do reach the shadow pass: Renderer.ts:2210 batches the explicit items, and Renderer.ts:625/794 passes the same items, filtered only by castShadow !== false, into ShadowPass.
(d) Explicitly instanced items cast a shadow from only one copy, at the item's modelMatrix.
(e) Alpha-mask/cutout casters are rendered as solid quads. Blended materials are dropped from shadows entirely by isTransparentCaster (ShadowPass.ts:68, 206-212).

The same DepthPass is used by ShadowPass.ts:104 (spot/directional and the 6 point-light faces in Renderer.ts:1545), by CascadedShadowPass (CascadedShadowMaps.ts:418-428, via ShadowPass), and by NativeFrameGraphBindings.ts:77/88.

*Counter-evidence:* I found nothing that skins, morphs, expands instances or alpha-tests shadow casters. There are no CPU-skinning helpers in the shadow path, and rg finds no reference to skinning, morph or instanceTransforms in ShadowPass.ts, DepthPass.ts or CascadedShadowMaps.ts.

Two refinements to the claim:
- Instanced and static-batched casters are not shadowless. They cast exactly one copy, for batches at the identity transform. So the claim's "wrong" is more accurate than "no", except where that single copy falls outside the light frustum.
- Fully transparent (blend) casters cast no shadow at all, because ShadowPass filters them out. They are excluded, not drawn wrongly.

Static batching only applies when source.staticBatching is enabled on the explicit renderItems/collectRenderItems path (Renderer.ts:2200-2213).

*Scope:* This affects every renderer-owned shadow path that goes through DepthPass: directional/spot ShadowPass, point-light cube faces, cascaded shadow maps, and the production-runtime framegraph bindings. Static batching is opt-in through source.staticBatching. Skinned and morphed items are excluded from batching by isStaticBatchCandidate (Renderer.ts:2388-2397), so they hit only the bind-pose problem. Callers that pass a precomputed explicitShadowMap bypass this path. I did not check whether a WebGPU backend has its own depth shader, and I did no runtime or visual verification. This was a code trace only.

**Skeptic 2 (confirmed):** Confirmed, with sharper detail. Every renderer-owned shadow path ends in the same DepthPass: directional/spot (Renderer.ts:1412), CSM (CascadedShadowMaps.ts:420 builds a ShadowPass), point faces (Renderer.ts:1543), and the frame-graph binding (NativeFrameGraphBindings.ts:77/88). ShadowPass.ts:104 always creates `new DepthPass`. DepthPass.drawCaster (DepthPass.ts:59-87) sends only a_position, a single u_modelViewProjection = lightVP*modelMatrix, and no instanceCount. The aura3d/depth shader (ShaderLibraryCore.ts:784-805) is position-only with no discard. As a result:
(1) Skinned items (RenderItem.skinning, GPU palettes) cast shadows in bind pose.
(2) Morph targets are ignored.
(3) Items with instanceTransforms draw one copy at the item's modelMatrix, with every other instance dropped. That is wrong shadows, not no shadows.
(4) Renderer static batching (SceneOptimization.ts:209-216) emits modelMatrix=identity plus instanceTransforms. A batched group therefore casts one copy of the local-space mesh at the world origin, and the real copies cast nothing.
(5) Alpha-mask/cutout materials cast solid quads. Blended materials are dropped as casters entirely (ShadowPass.ts:68, 206-212).
Two more points: casters are filtered with castShadow !== false (Renderer.ts:625/794), and they are taken after frustum culling and batching (Renderer.ts:2209-2210), so off-screen casters are culled too.

*Counter-evidence:* I found no alternate path that skins, instances, or alpha-tests shadow casters. An rg for skinned or instanced depth/shadow shaders in packages/rendering and packages/engine found nothing. Mitigations exist only at the content level:
- Aura Clash's instanced crowd sets castShadow:false (CrowdInstances.ts:139,151).
- Aura Clash's arena backdrop is pre-merged with consolidateStaticMeshes (AuraClashArenaApp.ts:860-884), so it has unique geometry and is unlikely to form instanced static batches.
- Static-batch singletons pass through with their real modelMatrix (SceneOptimization.ts:195-205), so batching only breaks shadows for groups of 2+ items that share the same geometry and material.
- Games without a shadow-casting light are unaffected: createProductionRuntimeShadowOptions sets enabled = Boolean(shadowCaster) (engine agent-api/index.ts:12959-12963).

*Scope:* Games do hit this path.
- Aura Clash: the side-view preset enables shadows (GameRenderPreset.ts:344-345, used via shadow: renderPreset.shadow at AuraClashArenaApp.ts:1421). The lighting rig is created with shadows:true and the stage spot casts. The fighters are GPU-skinned (a skinningBindingCount check throws at :892), and their render items come straight from actor.collectRenderItems() with castShadow undefined, so they are casters. Their shadows are therefore bind-pose. staticBatching:true is also set (:1392).
- Engine createAuraApp routes: the engine sets staticBatching: !temporalRequested for every route (agent-api/index.ts:13994). Any repeated geometry+material pair in any showcase game with a shadow-casting light therefore casts at the origin. Engine primitives with node.instances get instanceTransforms (index.ts:13980) and cast only one copy.
- Games that combine instancing with shadow-related code: neon-swarm, skyline-runner (foliage), turbo-drift-circuit (scenery), courier-rush (city), blockfall-reactor, rooftop-buckets, smart-city-control.
- Skinned or animated characters appear in Aura Clash fighters, gallery-shift guards and mech-hangar assembly.
I did not run anything to confirm per-game that each light has castsShadow set, or what castShadow defaults to on each node; the grep shows shadow-related keys in most games. "Wrong or no shadows" should read: instanced = only one copy; batched = one copy at the origin with the real ones missing; blended = none; masked = solid.

## C5. verdicts: confirmed, partially-true
**Claim:** Cascaded shadow maps can never run from the root createAuraApp path because Renderer requires a PerspectiveCamera instance and the bridge passes only {viewProjectionMatrix}; shadow fit is to camera-culled item bounds without texel snapping; filtering is manual NEAREST compare rather than hardware sampler2DShadow (Renderer.ts ~1387-1399, ~1964-1986, ShadowPass.ts).

**Skeptic 1 (confirmed):** This is true in the current checkout. Two line pointers need small corrections.

(1) CSM gate. Renderer.ts:1387-1399 calls executeRendererCascadedShadowMap only when three things hold: `light instanceof DirectionalLight`, `options.camera instanceof PerspectiveCamera`, and `(cascadeCount ?? 1) > 1`. The root createAuraApp bridge builds `const cameraLike: CameraLike = { viewProjectionMatrix }` (engine/src/agent-api/index.ts:14006). It passes that object, or no camera at all when the policy is auto-frame. resolveCamera (Renderer.ts ~2936-2975) returns `camera: resolved` only for real Camera instances, so `resolvedCamera?.camera` is undefined at Renderer.ts:629/798. There is a second, independent blocker: createProductionRuntimeShadowOptions (agent-api/index.ts:12942-12972) never sets cascadeCount, and nothing in packages/engine/src sets it.
