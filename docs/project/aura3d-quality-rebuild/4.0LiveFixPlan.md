# Aura3D 4.0 Live Fix Plan — Trash & Rebuild to Three.js Parity (REVISED)

Status: PLAN ONLY. No implementation started. This revision supersedes the
repair-in-place draft after the owner's 2026-10-13 decision: **trash the
showcase games in full by default; salvage only what proves it deserves to
survive; rebuild fresh on the current engine so no old scene code carries
forward.** The 4.0.0 npm publish staged at `24aa1390c` is FROZEN and its
release plan is void. Sources: 2026-10-12 parity root-cause audit of this
repo + owner production screenshots of `aura3d.auraone.ai`.

## The Decision (owner, binding)

- Default verdict for every showcase game is TRASH (scene + asset set), not repair.
- A game is salvaged only by earning it in Phase 2 (AuraClash is the owner's named candidate; others may qualify on the same evidence bar — none are pre-approved).
- Salvage never means keeping the old scene: at most, proven `src/gameplay/**` logic modules and the game design carry over. Scenes, post chains, and GLB sets start fresh regardless.
- Old code does not ride along: `src/legacy/**`, the `DEFAULT_ON` dispatcher, flag-off render branches, and the degraded fallback runtime are deleted, not maintained in parallel. One maintained scene and one maintained render path per surface when this plan ends.
- The engine parity fixes (Phase 1) still happen in full: the library is the shipped product, and fresh games built on a broken renderer would inherit the same bright/shiny/blurry defects.

## Goal

Ship a showcase where every surviving game is a fresh build on the fixed,
current Aura3D engine — art-directed asset sets, correct color/lighting/AA/
resolution, working input — at Three.js parity or better, and where games
that cannot earn salvage are gone and the game count is restated honestly.

## Success Criteria (per surviving game, on the live URL)

- [ ] Boots a single fresh scene from `src/main.ts` on current APIs (`createAuraApp` + genre kits); no `src/legacy/` directory, no dispatcher, no `?a3d-qr` token needed.
- [ ] Renders through the production backend only (diagnostics prove it; the silent safe-basic fallback no longer exists as a shippable path).
- [ ] Canvas resolution ≥ CSS × min(devicePixelRatio, 2); MSAA active; no authored FXAA-over-MSAA, no sub-1.0 DPR.
- [ ] Sane grade: total exposure ≤ ~1.1, saturation ≤ ~1.15, HDR-threshold bloom; passes the art-direction rubric against a Three.js genre reference frame.
- [ ] Every visible GLB passed the asset coherence gate (Phase 3): right style, right scale language, textured with normal+MR unless the game's art direction is explicitly flat.
- [ ] Move/look/primary-action/reset verified through real input in a browser session (L4), gameplay probe LIVE.
- [ ] L4 acceptance PASS with margin at un-lowered thresholds; live bundle hash matches the merged commit.

## Phase 3 — Fresh rebuilds (PORT and REBUILD games)

Order per game is fixed: art direction first, assets second, scene third.
Skills governing this phase: `aura3d-art-direction` (look recipe + look-dev
loop), `aura3d-assets` (admit/inspect/validate/type GLBs), `aura3d-browser-game`
(genre kits), `aura3d-scene-authoring`, `aura3d-character-animation` where rigged.

### Per-game rebuild checklist (repeat verbatim for each surviving game)

- [ ] Look recipe: genre reference frame (Three.js example or captured target) + written look preset committed under the app (palette, key light, fog, post budget from Success Criteria) BEFORE scene code.
- [ ] Scaffold: start from the matching template — `templates/mini-game`, `templates/racing-starter`, `templates/falling-blocks-starter`, `templates/fighting-game`, `templates/character-controller` — or current `createAuraApp` + genre kit (`game.platformer` / `game.racing` / `game.fallingBlocks` / `game.fighting`) when no template fits. New scene lives at `apps/<game>/src/main.ts` + fresh modules; PORT games re-import only the auditioned `src/gameplay/**` modules.
- [ ] Fresh asset set with coherence gate: EVERY visible GLB (hero, props, set dressing, environment) is admitted via `assets search`/`resolve`/`add`, inspected (`assets inspect`, `--animation` for rigs), and judged against the look recipe for style/scale/palette coherence — default is replace; an old asset is reused only if it passes inspection AND matches the recipe (record keep/replace per asset in the PR). Minimum bar: textured, normal+MR present, ≥1024 (prefer 2048) maps, sane metallic — unless the recipe is explicitly flat-shaded, in which case materials/HUD/copy all commit to flat.
- [ ] `assets validate --release` clean; `assets typegen` regenerated; scene references only `model(assets.x)` from the new `aura.assets.json` / `src/aura-assets.ts`; old asset registrations deleted.
- [ ] Scene on current defaults: engine ACES 1×1, no authored FXAA, DPR default, bloom only if the recipe calls for it within budget; no `scenery.ts` mega-rig, no `effects-pass.ts`/`post-v2-retune.ts` carry-overs; lights authored in physical terms post-E3.
- [ ] Input through current `GameRuntime` (E5 raw pointer where look is needed; pointer lock requested on canvas gesture for FPS); deterministic reset; objective + win/fail visible in HUD.
- [ ] Vehicle games: contact uses `packages/engine/src/agent-api/VehicleChassis.ts` per-wheel samples against the SAME mesh that renders (no separate visual shell + constant lift — the Turbo `ROAD_DETAIL_SURFACE_LIFT` pattern at old `main.ts:245,257-265` is banned in rebuilds); lap-sweep capture proves no tire below the rendered surface.
- [ ] Look-dev loop: L4 capture → rubric judge vs reference frame → iterate until pass; capture set committed as the game's new acceptance baseline (old over-bright baselines deleted, thresholds unchanged).
- [ ] Deletions in the same PR: `apps/<game>/src/legacy/`, `apps/<game>/src/v2/` (unless the rebuild literally is the v2 scene promoted and renamed), the `DEFAULT_ON` dispatcher in `apps/<game>/src/main.ts`, dead assets, dead specs that only exercised the old scene (replaced by new-scene specs).

## Risks / Open Questions

- Scope honesty: trashing 19 scenes is the expensive option — pilots exist to price a rebuild before committing to all of them; SALVAGE.md + pilot results are the owner's last cheap exit to a smaller showcase (fewer, better games is an acceptable outcome; padding the count is not).
- E3 changes every light in the engine at once and remains the highest-risk step; it lands behind its lane with the Three.js side-by-side as the promotion gate, before any rebuild tunes lights.
- Fresh assets are a licensing/quality supply problem, not just a search problem: if the catalog lacks coherent sets for a genre, that game goes DROP rather than shipping mismatched GLBs again.
- Live identity (Phase 0) may show production is stale; that changes attribution of the owner's screenshots but not this plan — the shipped scenes are legacy regardless.
- Timeline driver is asset art direction per game, not code; batches of 2/PR keep review honest at the cost of calendar time, which the owner accepted by choosing trash-over-fix.
