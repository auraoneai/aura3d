## 0. Findings in ten lines

1. The 25 games are exactly the `liveGameCount: 25` records in `docs/workflows/game-inventory.json` (generated from `tools/site/games.catalog.json`; `kind: game`, `status: live`). 14 keep their code in `apps/showcase-<slug>/src`; 11 are thin mounts (`apps/showcase-*-port/src/main.ts`, about 100-500 lines) over `examples/<name>/` (section 2).
2. **No game, example or template imports a removed 4.x API.** Scan over all 209 `apps/*` + `examples/*` directories for the 38 removed root values (B14), the nine removed subpaths (B15) and a root `createGame` (B1): zero hits. Every `createGame` import is from `@aura3d/engine/game` (e.g. `apps/showcase-iron-crown/src/main.ts:12`). The only names that look like removed ones are valid replacements: `A3DRenderer` from `@aura3d/engine/renderer` (`apps/loader-ktx2/src/main.ts:11`), `GLTFLoader` from `@aura3d/assets` (`apps/editor/src/export/ProjectSceneRuntime.ts:1`), `createProductConfiguratorWorkflow` from `@aura3d/workflows` (`examples/product-configurator/main.ts:2`).
3. Two real leftovers on removed subpaths: `packages/create-aura3d/templates/animation-studio/scripts/render-core.ts:336-346` and `render-live.ts:194-204` alias `@aura3d/engine/{advanced-runtime,production-runtime,assets/browser,rendering}` to `dist/` files and gate the whole alias block on `existsSync(DIST("engine/advanced-runtime/index.js"))`. On a 5.0 dist that guard can silently turn false (section 6, T-1).
4. Dependencies: all 25 games declare `"@aura3d/engine": "workspace:*"` (plus `@aura3d/animation` for Pip's Big Leap); the in-repo resolution is `vite.aliases.generated.ts:97` to `packages/engine/src/public/index.ts`, i.e. the games already build against 5.0 source. `package.json` `version` fields are stale (`4.5.0` / `0.1.0`). The 20 create-aura3d templates are already pinned to exact `5.0.0` (`packages/create-aura3d/templates/mini-game/package.json`). Only `apps/world-war-x-showcase` pins `@aura3d/engine@1.0.5`.
5. "Upgrade for 5.0" is therefore not a compile-fix job for games. It is a capability-adoption job, and the risk is visual: the 4.7.x frames of record (`evidence/game-upgrades-47/*`) were tuned on the software-WebGL2 runner and a major release that changes defaults (color pipeline, lookAt, depth, transparency, shadow/AO) can move them.
6. Biggest legacy debt is **hand-written GLSL `material.custom`**: 11 port examples carry 18-82 `material.custom`/GLSL regex hits each (e.g. `examples/roadster-hours-port` 82, `examples/saiyan-snake-way-port` 59, `examples/where-the-wind-wanders-port` 62, `examples/heatsink-port` 63) and `apps/showcase-roadster-rush` 41. These sources are GLSL-only (`glsl: { vertex, fragment }`, `#include <a3d_lights>`); none has a WGSL twin or a shader graph, so none can run on the opt-in native WebGPU backend (`renderer.backend: "webgpu"`).
7. Second debt: hand-rolled DOM HUD (`createHud` x3-6 in 7 games: top-tennis, heatsink, teleoperator, iron-crown, pips-big-leap, aura-fc-3d, roadster-hours-port) while 5.0 adds `game.shell.setLoadingProgress()/track()` (B10) and `bindPointerInteractions`; third: explicit `pixelRatio` / `qualityProfile` overrides in 13 games (12 ports and Slingshot Siege plus Aura Slam's rig harness) contradicting the `llms.txt` never-list (section 4.2).
8. Physics: only Slingshot Siege uses engine physics (`physics.world`, `apps/showcase-slingshot-siege/src/game/sim.ts:22,196`) and no game uses hinge joints; the prototype `showcase-vault-breakers` already carries the 5.0 relative-hinge-limit note (`src/gameplay/table.ts:51`). B-row hinge/lookAt changes do not touch the 25.
9. One B2-type exposure: `examples/aura-slam/view/renderer.ts:361` builds `({ nodes: { require: rigReq } } as unknown as AuraApp)`. It compiles (cast), but it is a partial `AuraApp` double that will not satisfy the new required members; fix to a narrow interface (Aura Slam, S).
10. Already-ahead items to protect: `apps/showcase-aura-diamond-3d/src/scene.ts` was hand-edited in `ccdc9cfe7` because the retired `@aura3d/engine/lanes` `probes` builder is not in the 5.0 public surface; the 5.0 examples-source work fixed 36 catalog examples in `ccdc9cfe7` (list in section 3.4).

## 1. Scope and how "the 25" were chosen

- **Definition used.** The site and gate tooling count a "game" as an entry in `docs/workflows/game-inventory.json` with `kind: "game"` and `status: "live"` (`liveGameCount: 25`; genres racing 8, sports 5, action 4, platformer 5, arcade 3). `tools/game-checks/lib/index.mjs:471` iterates exactly that set and `tools/site/check-game-count.mjs` guards the count; the 5.0 route-tier commit `cf8d4fd85` records "25 live games = development showcase". `docs/project/showcase/apps-classification.md` lists the same 25 as `development showcase`, with `aura-clash-showcase` also labelled `development showcase` but absent from the live inventory (not counted as a game: no inventory record).
- **Why not more.** About 20 other `apps/showcase-*` routes are playable prototypes or blocked (`showcase-bank-shot`, `-vault-breakers`, `-aurora-lander`, `-blockfall-reactor`, `-skyline-runner`, `-turbo-drift-circuit`, `-deep-recovery`, `-gallery-shift`, `-gravity-post`, `-neon-swarm`, `-patrol-wing`, `-rooftop-buckets`, `-siege-golf`, `-courier-rush`, `-pulse-tunnel`, `-mech-hangar`, `-meshy-relic-pilot`, `-orbital-defense`; plus unclassified `-bean-brawl-race`, `-kart-havoc`, `-turbo-ball`, `-red-zone-3d`); they are in section 5 with a lighter plan.
- **Evidence the 25 are inside the 5.0 example catalog.** `discoverExampleCatalog` (`tools/agent-examples/index.ts:201-300`) keeps a `development showcase` route in the catalog when `tools/site/games.catalog.json` lists it (`documentedShowcase`, line about 266). So the 25 are `documented-example:apps/showcase-*` entries that the packed-candidate `examples-source` stage (shards packed-c1..c4, `tools/remote-acr/run-source5.sh`) builds against the packed 5.0 archives. I could not read the pass 011/014 report files (they are in `tests/reports`, out of this task's scope), so "compiles on 5.0 per pass 011/014" is stated below as "catalog-covered", and the parent should confirm per-id status from `examples-source.json` before relying on it.

## 5. The 25 games: per-game plan

Common to every game (not repeated): `package.json` uses `@aura3d/engine: workspace:*`; the in-repo alias resolves to 5.0 source; catalog-covered by `examples-source` as a `development showcase` documented example; no removed 4.x API (grep); must keep `node tools/game-checks/run.mjs <slug>` clean (checks: quickbar, canvas-resize, fixed-step-presenter, hitstop-time, touch-input, lighting, art-direction, look-identity, prop-exclusivity, luma-band, upgrade-guide, page-parity...). Shared-work items W-1..W-8 are in section 7; each game's "Do" list is on top of them.

Verification shorthand: **GC** = `node tools/game-checks/run.mjs <slug>`; **UT** = the game's targeted vitest folder (`tests/unit/<game>` / likeness-audit) on the allowed local path or ACR; **CAP** = the parent's single coordinated ACR capture (`tests/browser/game-luma-capture.spec.ts`, 25 s and 60 s shots, `GL_SETTLE`), compared with `evidence/game-upgrades-47/<slug>/f48*/f49*/f50*/frames`; **RG** = real-GPU headless-false pass for any EXPERIMENTAL flag (`tools/real-gpu/run.sh`).

Risk legend: **visual risk** = chance that 5.0 engine changes alone, or the adoption, move pixels versus the 4.7.x frames of record. Engine-wide 5.0 changes that can move pixels for any game: regenerated neutral environment (`S5-WP04-05`, `public/aura-environments/{neutral,indoor}.*`), render-order across split phases (`S5-WP31-03`, `planForwardPhaseOrder`), motion/temporal history rewrite (`S5-WP06-02/05/06`), frame-path perf commit `86667a6b8` (cached context attributes, VAO dedupe; pixel-neutral by intent), `lookAt` now applied to models (none used), color pipeline defaults unchanged.

## 9. Prioritized upgrade order

Principle: engine alone already upgrades every game (they build from 5.0 source), so order by (a) risk of silent drift, (b) availability of capability gain, (c) cost.

1. **Wave 0 (shared, parent only):** W-1, W-2, W-5, W-7, W-8, then W-3 baseline drift capture. Output: a per-game "moved / unchanged" table. No per-game work starts before this, because changes made on top of an unknown drift are impossible to judge.
2. **Wave 1, low-risk adopters (8 games, 5.0 stable features, S effort):** aura-hoops-3d, aura-diamond-3d, dot-dash-3d, bunker-zero, top-tennis, slingshot-siege, iron-crown, pips-big-leap. Items: A1 loader, A2 overlay, B2 fix, lab flags A3/A5 where no GLSL-only code exists (hoops, diamond, bunker, dot-dash, top-tennis, slingshot). Local-only lanes; parent captures once.
3. **Wave 2, shader-light games:** cross-hop, aura-fc-3d, aura-links-3d (water A4 pilot), teleoperator, heatsink, roadster-rush (the first A4 candidates: decals, wakes, plume).
4. **Wave 3, A4 pilot on the smallest port:** last-train-port (21 shader hits) to prove portable materials, then silt-and-signal-port (water). Gate: pixel diff of converted materials against GLSL on WebGL2 before WebGPU.
5. **Wave 4, heavy GLSL ports (no rewrite by default):** strange-orbit, splat-rush, serpentine, drift-and-deliver, heatsink-port, ninja-runner, roadster-hours, where-the-wind-wanders, cloud-runner. Default: keep GLSL, mark WebGL2-only, run engine-drift capture only; convert only if the pilot proves a clean pattern (decision D4).
6. **Non-games last:** G2 candidates (public, need paired frames), G5 real-GPU evidence runs, G6 doc refresh.

# Part B. AI-authoring docs upgrade (llms.txt, agent docs, skills, recipes)

**Goal.** Let Claude and GPT agents produce procedural geometry, shaders and lighting in Aura3D, without admitted models, in far fewer turns, by teaching them from the context they read first and by reusing what they already know about three.js. This is a docs and skills work stream. It ships as a 5.0.x docs release after 5.0.0 (the docs are bundled into `create-aura3d`, so editing them during the 5.0.0 freeze would invalidate the source pass). It never changes engine behavior.

**Evidence that motivates it.** `evidence/agent-eval/REPORT.md` (cold-start trial, @aura3d/engine 4.1.2, docs-only agents, same model for both libraries): the PBR-cube task took Aura3D about 40 turns and about 150 s against about 4 turns and 14 s for three.js; the 10,000-instance forest task finished 0/3 at a 40-turn budget and 2/3 rendering at 100 turns, against 3/3 in about 4 turns for three.js. Aura3D agents opened about 19 package and type files per task (three.js: 0). They were reading types because the docs did not answer the question directly. The October quality autopsy scored Aura3D mean 3.6 against three.js 5.4 on the benchmark scenes. These numbers are old; WP-D7 re-measures them.

**Rules for this work stream.**
- Public copy stays sales-only: Aura3D is a standalone engine, never "built on three.js" (see the memory note `sales-only-marketing-copy`). A translation table says "if you would write X, write Y", nothing else.
- Everything shown must run: every recipe is built, typechecked and rendered on ACR before it is documented as working. No claim of parity or quality without root-only browser evidence (`docs/agents/claims-and-boundaries.md`).
- Edit canonical skill sources in `packages/aura3d-cli/skills/`, then `pnpm skills:sync`; `pnpm check:skills` must pass.
- No new test suites beyond the minimum that gates the new docs (existing docs-lint, llms size check, recipe build check).

# Part C. 5.0.1: hotfix and everything the 5.0.0 release left open

**Goal.** Ship a 5.x release that renders every one of the 25 games and the 20 templates in a real browser, carries the known-issue fixes, has a passing browser acceptance run, and is promoted to `latest` only after a rendered-frame check. Part C supersedes the ordering in sections 9 to 11 of Part A until it is done.

## C0. What happened (facts)

- **2026-11-05 18:19 UTC:** 5.0.0 released from frozen commit `5e757c11f` (source pass 54/54; browser acceptance incomplete and disclosed). 25 npm packages, tag `v5.0.0`, GitHub release, `aura3d.auraone.ai` and the Wonder World app redeployed.
- **About 18:40 UTC:** checking the live site with a real-GPU Chrome (REA `capture_browser_scenario`) showed `RENDERER_MOUNT_FAILED: RenderDeviceError: Contact shadows require verified graph passes and depth participants. Nothing will draw.` on `/apps/showcase-top-tennis/` and `/apps/showcase-roadster-rush/`. The page rendered its HUD, the 3D canvas was black. The same game on the rolled-back 4.7.13 site renders fully. All 25 games share the engine and the default look, so all 25 are affected.
- **Rollback (done, reversible):** Cloudflare Pages `aura3d` production rolled back to deployment `a5d4a780-8e48-4779-80a0-febaf2d3490d` (4.7.13) and `aura3d-wonder-world` to its previous production deployment; npm `latest` moved back to 4.7.13 for all packages (`@aura3d/addons` has only 5.0.0), 4.7.13 un-deprecated, 5.0.0 deprecated with a warning; GitHub `v5.0.0` marked pre-release with a warning, `v4.7.13` Latest again. The 5.0.0 artifacts remain published (npm does not allow a clean unpublish) and the tag `v5.0.0` stays.
- **Side effects of the rollback to clean up in 5.0.1:** the `Superseded by 5.0.0 ... migration` deprecation messages on all older versions point at `https://aura3d.auraone.ai/docs/migration/4-to-5`, which is not live while the site is rolled back; 59 older GitHub releases carry a banner pointing at the (now pre-release) v5.0.0. Both are repaired when 5.0.1 ships (re-deploy the site with the migration page, re-point banners and deprecations to 5.0.1).
- **Where the guard lives:** `packages/rendering/src/Renderer.ts` (about L4228 and L5082) throws `CONTACT_SHADOW_DEPTH_UNSUPPORTED` whenever contact shadows are requested and `!frameHooks.contactGraphIsSafe() || gaussianSplats.length || scalarVolumes.length || !isUnmodifiedDefaultShaderLibrary(...) || !forwardDrawReplaySafe(...)`. The guard does not exist in 4.7.13. A twin guard throws `SCENE_CLIPPING_CONTRIBUTOR_UNSUPPORTED` for clipping combined with extra scene geometry.

## C1. Why it was not caught (the process failures to fix)

1. **No test ever loaded a game or a template in a browser with the real engine.** The source pass builds the catalog examples (`examples-source`) but does not run them; unit tests use mock devices; `tools/game-checks/run.mjs` is not part of any gate.
2. **The acceptance run that could have caught it was dismissed.** Browser acceptance failed 107 of 147 tests; most were harness defects, so the whole run was treated as harness noise instead of finding the 5 to 7 product signals inside it. A failing acceptance run must be fully classified (H harness, E environment, P product) before release, with every P resolved or accepted by a named decision.
3. **The post-deploy check only proved HTTP 200 and asset URLs.** The preview scan (`scan-live-site`) and `verify-asset-urls` do not execute pages. A page that returns 200 with a black canvas passes.
4. **Strictness was introduced as a hard throw on a default path.** 5.0 turned "cannot run this optional effect safely" into a mount failure. Optional effects on default looks must degrade and warn, never blank the scene; only `strict: true` may reject.
5. **Concurrent sessions and fragile scratch.** Another session released 4.7.14 and merged into `main` while the 5.0.0 release was in flight; scratch directories were deleted mid-release; background watchers died. Releases need a single coordinator, a lock note in the repo's shared area, and scratch kept in the repo's `tests/reports` or a durable path.

## E6. Spatial-data use cases and the 5.1 runtime (revised 2026-11-07 after owner review)

Owner direction: Aura3D is our proprietary engine and the objective is a commercially competitive, high-performance, agent-native 3D and simulation platform that can power several AuraOne products (robotics, AV, simulation, digital twins, AI-driven environments). We do not default to three.js or deck.gl because Aura3D lacks something today; they are comparative benchmarks and optional interoperability targets. We do not try to recreate three.js feature for feature, we do not treat missing features as permanent, and we claim no competitive advantage until measured. The engine roadmap (5.1) is separate from AuraOne application development, and the frozen 5.0.3 candidate is not destabilised by any of this.

Three separate questions: (1) what can Aura3D do today (audit E6-00), (2) what must it support to be commercially competitive (E6-01 to E6-05), (3) which applications AuraOne builds on it (E6-06). The standing question to answer with evidence: does owning Aura3D yield measurable advantage in developer productivity, reliability, automation or performance enough to justify an independent engine.

Repo scan summary before the audit (unverified in depth): rendering pieces exist (`points()` taking plain arrays, lines compiler, instancing, glTF skeletons and clips, fixed-step deterministic loop, PLY/STL/3MF/splat importers, volumes, `@aura3d/react`, editor-runtime review panels as state models); nothing found for URDF, ROS bag or MCAP, OpenDRIVE/Lanelet/GeoJSON, IFC/USD/3D Tiles, synced multi-topic timeline or 3D annotation.

- [x] **E6-00 Evidence-backed assessment (done 2026-11-07, `docs/project/e6-00-spatial-runtime-assessment.md`: 88 findings with path:line, 57-gap register with effort, risk and acceptance criteria, runtime path design sketch, benchmark plan; nothing measured yet).** Scope was: For each capability: what exists (source references), what is missing, whether the gap is architectural or application-specific, what closing it takes (effort, regression risk, dependencies, acceptance criteria). Covers: scene update paths (declarative recompile vs mutable runtime), typed-array point buffers and incremental geometry updates, instance transform updates, trajectories, picking/raycast, labels, measurement, camera control, `@aura3d/react` embedding and canvas/lifecycle isolation, determinism/state replay, diagnostics for agents.
- [ ] **E6-01 Reproducible benchmark suite.** Points 100K / 250K / 1M (float32 xyz plus packed 32-bit color: about 16 MB per 1M-point frame; full replacement at 60 Hz would be about 960 MB/s, so render rate and sensor rate are measured separately); instances 1K / 5K / 10K; sensor update 10 / 20 Hz; display 30 / 60 FPS; interactions: picking, labels, measurements, camera motion. Record p50/p95 frame time, CPU and GPU time, memory, dropped frames, buffer upload cost, and exact hardware, browser and driver. Compare with equivalent three.js implementations on identical hardware, browser and datasets. Engineering targets for investigation, not claims.
- [ ] **E6-02 Remediation decision (replaces the earlier pass/fail gate).** If Aura3D underperforms, diagnose whether the cause is CPU overhead, GPU bottleneck, scene recompilation, buffer management, shader execution or API architecture; estimate cost and risk of fixing it before recommending any other engine. Keep Aura3D as the preferred runtime.
- [ ] **E6-03 High-frequency runtime path.** Two complementary update paths: declarative scene definition (persistent objects, materials, physics configuration, scenario descriptions, typed relationships) and a mutable high-frequency path (typed-array buffers, incremental geometry updates, instance transforms, sensor streams, live animation) that does not recompile the scene and preserves the typed-scene architecture. Engine-wide benefit, not robotics-specific; declarations change, so 5.1 (minor).
- [ ] **E6-04 Embedding and interoperability audit.** Aura3D must integrate into an existing React application without owning routing, global state or the page: audit `@aura3d/react`, canvas and camera lifecycle, multiple instances, picking, measurement, labels, component isolation.
- [ ] **E6-05 Modular format adapters, not core parsers.** ROS, MCAP, URDF, USD, IFC, GeoJSON, OpenDRIVE and similar are assessed as extension packages or data adapters on top of a runtime (renderer, GPU buffers, scene graph, picking, physics interfaces, spatial APIs). Capabilities to learn from Foxglove's product (not its renderer): time synchronisation, transform (TF) trees, point clouds, model inspection, measurements, recorded-data replay.
- [ ] **E6-06 AuraOne first proof of viability.** Use AuraOne's own robotics and evaluation workflows (Human Data + Evals viewer) as the first commercial proof; application work is tracked separately from the engine roadmap.
- [ ] **E6-07 Agent-native scenario generation and verification (priority).** Structured scenario schema; deterministic state-replay tests; machine-readable validation and failure diagnosis; an MCP interface that lets agents create, modify, execute and evaluate scenes. Differentiation hypothesis: the combination of typed scenes, predictable mutation APIs, machine-readable diagnostics, reproducible simulation state and automated verification. MCP tooling alone is not unique (it can wrap three.js); do not claim the advantage until demonstrated.
- [ ] **E6-08 Digital twins stay on the roadmap.** Defer application-specific functionality (IFC/USD/3D Tiles loaders, huge-model streaming) but keep the architectural requirements (LOD and streaming hooks, picking, large-scene throughput) so they remain possible.
- [ ] **E6-09 Reference cases, verify from primary sources before any sales use.** Foxglove (confirms its 3D panel was rebuilt on three.js; product capabilities per its docs: time sync, transforms, point clouds, model inspection, measurements, replay); AWS IoT TwinMaker scene viewer (React Three Fiber); Foresight AI case study (names both three.js and Uber AVS; Uber AVS itself is XVIZ, streetscape.gl and deck.gl, so treat the combination as two separate architectural claims); realvirtual WEB (three.js).
- [ ] **E6-10 Per-improvement record.** Every proposed improvement lists source references, acceptance criteria, benchmark evidence, dependencies, regression risks and effort estimate.
