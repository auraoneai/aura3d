# Aura3D 4.7.10 vs 5.0 visual comparison

Status: **template, not a result.** Nothing here has been captured. The source preparation (plan, capture spec, contact sheet, launcher group) is committed-ready; the capture runs once, after 5.0 acceptance passes, and the "Results" section at the end is filled in from that run.

What this is for: after the 5.0 acceptance batches pass, take **one** extra remote capture of 5.0 and set it beside **existing** 4.7.x frames of record, so a reader can see what changed on screen. No baseline is re-captured. It is a prompt to look at pixels, not a gate and not proof that 5.0 "looks better": see the caveats before reading any number.

## 4. How to run

Prerequisites: acceptance batches 1 and 2 finished and fetched (`tests/reports/native-5/<RUN_ID>-b1` and `-b2`), the same frozen `HEAD` and gate record, `build-plan.mjs --check` green, and the parent has recorded the cloud cost/lifecycle contract (14 fields) for one more run. Only the parent launches it; no lane launches its own.

```sh
export AURA3D_CODE_COMPLETE_GATE=tests/reports/native-capabilities/code-complete-go.json
# plan only (no gate, no Azure): 6 shards, about 3 views each
ACCEPT_GROUPS=visual-compare PLAN_ONLY=1 tools/remote-acr/run-acceptance5.sh
# the capture: its own invocation, own SAS, own image build
ACCEPT_GROUPS=visual-compare RUN_ID=native-5-accept-001-vc tools/remote-acr/run-acceptance5.sh
```

Why a separate invocation and not "batch 2": batch 2 is already full. The planner simulation puts both lanes at about 5,200-5,260 s of the 5,280 s start limit (7,200 s SAS minus a 1,800 s run and a 120 s margin), so adding six shards pushes the evidence stage into a third batch. The group is therefore `optional = true`, `split = tests`: absent from the default plan (the default plan and its two batches are unchanged), and planned alone with `ACCEPT_GROUPS`. `split = tests` lets the planner use more than one shard for the single spec file (the spec runs in Playwright parallel mode, so `--shard=i/6` splits views).

Time and cost, estimated, not measured: a 25 s shot completes about 167 s after ready (median of 103 retained shots, 25 to 510 s) and ready takes about 41 s (median, up to 223 s), so a view is about 3.5 min median and up to 12 min worst case; a 60 s shot is 5 to 12 min. Four views have 60 s-only baselines (orbit-neutral, bunker-indoor, tennis-text, crown-skinned) and cost more. Six shards at the planner's 23 min estimate, two at a time, is about 70 min wall clock. Gross cost at 0.0002 USD/s per run (2 vCPU) is at most 6 x 1,800 s x 0.0002 = 2.2 USD plus one image build, under the 5 USD per-run ceiling; the 10 USD per-task total is summed over every agent, so check the ledger first. A worst-case tail that hits the 1,200 s Playwright timeout is recorded as no-data for the unfinished views, never as a pass.

Spec switches (environment of the shard, set through the launcher's environment if needed): `VC_VIEWS=orbit-glass,wind-day` to capture a subset, `VC_SHOTS=25,60` to add the 60 s shot where both baselines exist (only worthwhile for static views), `VC_RUN=<name>` to name the output folder (default: the ACR run id).

After the shards finish, the launcher fetches each shard into `tests/reports/native-5/native-5-accept-001-vc/<shard>/artifacts/`. Build the sheet (host side, no Azure, no browser):

```sh
node tools/release/visual-compare-5.0/contact-sheet.mjs \
  --frames tests/reports/native-5/native-5-accept-001-vc \
  --acceptance-run tests/reports/native-5/native-5-accept-001-b1 \
  --acceptance-run tests/reports/native-5/native-5-accept-001-b2 \
  --out tests/reports/visual-compare-5.0/sheet-001
```

Outputs: `index.html` (summary, table, environment, panels, problems), `summary.png`, `panels/<id>.png`, `metrics.json`. Options: `--threshold 24` (a pixel counts as changed when its largest channel differs by more than this; 24 is the level the retained noise analysis used), `--amplify 4` (heat map gain), `--lossless` (compare the PNG instead of the JPEG re-encode), `--strict` (non-zero exit when a paired view has no 5.0 frame or a baseline is missing or no longer matches its sha256).

## 5. How to read it

Each paired panel is `[4.7.10 baseline | 5.0 | amplified |difference|]`, with these numbers in the header and in `metrics.json`:

- `meanAbsDiff`: mean absolute difference over all channels, 0 to 255.
- `pctChanged`: percent of pixels whose largest channel difference exceeds the threshold (default 24).
- `maxRegion`: the cell of an 8 x 6 grid with the largest mean difference (pixel rectangle), where to look first.
- `lumaMean`: Rec.709 luma mean of both frames and the difference (5.0 minus baseline). A uniform brightness shift is an exposure/tone change, not a content change.
- `bandDelta`: signed mean-RGB difference of two static bands, `sky` (rows 0-120 of 720) and `foreground` (rows 500-720). These are the "static region" checks of the blind-panel rule below: agreement within about 1.2 per channel on a band means the lighting of that band did not move.
- `comparedAs`: `jpeg` when the 5.0 side is the JPEG re-encode (like for like with the JPEG q0.7 baselines, the default) or `png`; `resized` is true if the 5.0 frame had a different size and was stretched to the baseline's.

A reading procedure that respects the noise: (1) check `problems` first (missing frame, baseline sha mismatch, HTTP 4xx in `meta/*.json` `badResponses`, `info.texPending` above 0, a black or error frame); (2) for `motion: static` and `light` views, read `bandDelta` and `maxRegion` and look at the heat map; a localized hot cell on a real object is a candidate change, a uniform low-level red is codec and exposure noise; (3) for `animated` views, ignore moving-object regions and judge only static bands and the source diff; (4) where `changedIn4710` is set, the model addition is expected; (5) only then form an opinion by looking at the two frames, and if it matters, run the blind panel (three judges, neutral A/B copies, at least 2 of 3 must prefer the new frame; anything less is "unverified", not "worse").

## 6. Caveats (do not skip)

- **Animated scenes are noisy.** Traffic, runners, crowds and particles are time-driven. On the software runner a "25 s" shot completes about 3 minutes after ready and a "60 s" shot 5 to 12 minutes after ready, and even two captures of identical code differ: same-code recaptures of animated views changed on 28 to 31 percent of pixels over 24, and the same frames flipped worse/same/better between panel runs. A large `pctChanged` on an `animated` view is expected and says nothing about 5.0. `light` views move only slightly; `static` is rare.
- **Software rendering on both sides, but not the same environment.** The baselines come from the 4.x ACR path (Playwright `legacy-chromium` project, `--enable-unsafe-webgpu --ignore-gpu-blocklist --enable-unsafe-swiftshader`, the Chromium and Playwright of that day), recorded only as "ACR software WebGL2 (SwiftShader), 1280x720". The 5.0 run uses the `chromium-automation` project with default launch options on the pinned Playwright image of the acceptance build. Both are SwiftShader in a container, but the browser build, driver version and flags can differ, which changes rasterization, MSAA and texture filtering slightly. **The 5.0 side records its environment in `environment.json`** (browser version, project, WebGL unmasked renderer and vendor, DPR, user agent, ACR run id, candidate freeze commit); **the baseline side is not recorded at that level** in the retained frames (rows hold `renderPath`, draw calls and timings, not the browser version or GL renderer). Fill both into the Results section; if the browser or renderer string differs, say so next to any conclusion. Neither side is real-GPU evidence.
- **The baselines are older than the release for some views and JPEG.** Phase 7 and 9 frames are from 2026-11-01 (about 4.7.6 to 4.7.8), f48 to f50 from 2026-11-02 (the 4.7.9 candidate); four views predate 4.7.10's own model swaps. They are canvas-only JPEG at quality 0.7, so a small codec noise floor exists even for identical renders (the sheet compares a JPEG re-encode of the 5.0 frame by default to cancel it).
- **Canvas-only.** DOM HUD, buttons and overlays are hidden by the capture style, exactly as in the baselines. "Text/UI" here means in-canvas 3D text, not the DOM HUD. DOM UI is outside this comparison.
- **Mocks and stand-ins.** If an app fails to load an asset, the page can draw a stand-in or a black frame (`VC_HTTP`, `badResponses`, a near-black luma mean). The acceptance image stages the gate's candidate file list; confirm the game GLBs under `public/aura-assets` and each game's folder were staged, otherwise views compare a stand-in against a real model. This was not checked in source, because staging needs the gate and Azure.
- **Showcase panels are not before/after.** Where the fallback is a sibling scene (for example `template:product-viewer`) the pair shows different scenes. Their diff number is shown only when a fallback frame exists and is not an improvement metric.
- **Not a gate.** Nothing in `contact-sheet.mjs` decides pass or fail. It does not change CODE_COMPLETE_GO or the acceptance totals.
- **Blind-panel rule.** A difference counts as better or worse only if a blind panel (three judges on neutral A/B copies, at least 2 of 3 agreeing) says so, after the static-band and source-diff checks above. A single side-by-side impression, including the author's, is not a verdict.
