# Aura3D 1.6 layers — what we own, what we integrate, what sits between

Derived from [`Aura3D-1.6-Architecture-Decision.md`](../../Aura3D-1.6-Architecture-Decision.md) and
governed by [`Aura3D-1.6-Replatform-PRD.md`](../../Aura3D-1.6-Replatform-PRD.md) §A.

> **Aura3D owns only the layers that create lasting competitive advantage over Three.js. Everything
> else is integrated, abstracted, or removed.**

## Layer 1 — Aura3D-owned core (the Three.js competitor)

Kept and strengthened. The renderer earns this place on evidence: 85 Khronos glTF assets render
in-browser against real Three.js at a median 6.73/255 mean-absolute-error, on a real WebGL2 device
(`WebGL2Device.ts`, ~700 `gl.*` calls) and a real WebGPU device with native pipelines.

- renderer (WebGL2 + WebGPU), scene graph, geometry, materials, shaders, lighting, shadows, textures
- animation rendering, postprocess, GPU resource management
- typed scene authoring and the public agent API
- asset intelligence: catalogue, provenance, hashes, bounds, role admission, semantic metadata
- CLI-driven typed asset workflows and deterministic project generation
- diagnostics, replay, runtime invariants, interaction auditing
- a migration path for Three.js developers (`packages/three-compat`)

**Honest standing, measured 2026-08-05 (WS-1.4):** 1.6x slower per frame and 2.83x larger than
Three.js on 512 lit PBR boxes. That is the gap the release has to close, not a footnote.

## Layer 2 — integrated external backends

Where a mature specialist library exists and owning the internals creates no advantage.

| Domain | Current | 1.6 direction |
|---|---|---|
| Rigid-body physics | `cannon-es` in **one file** of 12,631 lines, plus a hand-written `aura-js` solver whose divergence let joints be a silent no-op | Backend chosen by the **WS-4.2 bake-off**, not pre-decided. Permitted outcomes include no multi-backend abstraction at all |
| Audio | Web Audio, plus `packages/audio` and `engine/src/game/GameAudio` | Web Audio as the backend; one Aura3D audio layer above it (WS-3.2) |
| Asset codecs | `@loaders.gl/core`, `@loaders.gl/textures` | Keep |
| Navigation | own `Navigation`/`Crowd`/`Steering`, genuinely in use (8/5/2 app files) | Keep through P4; re-evaluate against the chosen backend's queries **afterwards** (WS-4.6) |

## Layer 3 — the Aura3D integration layer

The moat. Not "we wrote everything ourselves" — it is that Three.js has no answer to these.

- one consistent public API with backend abstraction beneath it
- deterministic runtime and replay
- semantic assets with provenance and role admission
- inspection, evidence, and **claim lineage** (see [`claim-lineage.md`](./claim-lineage.md))
- project generation and agent workflows
- application kits and game kits composed from the layers below

## What Aura3D is NOT

Every item below exists in this repository today as a hand-written implementation. That is the drift
1.6 reverses; **R11** requires an ADR before any of them is built again.

a physics engine · an audio DSP library · an ECS research framework · a behaviour-tree/GOAP/HTN AI
framework · a cloth simulator · a fluid simulator · a fracture or soft-body simulator · a video
encoding or publishing framework · a general-purpose state-management library · a navmesh generation
library

## The boundary rule

> Does owning this component make Aura3D a stronger direct competitor to Three.js, or create a
> genuinely better integrated platform around that competing core?

Yes → own and strengthen it. Valuable abstraction over weak internals → **keep the API, replace the
backend**. Neither → remove it.
