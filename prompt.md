## Why This Is Needed

The previous attempts failed because examples were patched around library gaps:

- GLBs loaded but were badly scaled, poorly grounded, hidden, deformed, or mismatched.
- PBR/high-resolution/HDR claims were not visually proven.
- Primitives were used as primary gameplay/world visuals.
- Racing and platformer examples became tiny 5-10 second demos instead of real games.
- Camera framing made objects disappear, crop, or look flat.
- Asset selection accepted unusable GLBs without enough quality grading.
- Documentation allowed agents to keep producing slop instead of enforcing quality gates.

This prompt exists to prevent that loop.

- camera integration
- runtime node mutation
- animation playback
- route/objective design helpers

Minimum standards for game examples:

- 60 seconds of meaningful playable content, not 5-10 seconds.
- At least 3 minutes of route/world design should be possible from the runtime and asset system, even if the showcase proof captures only representative screenshots.
- At least 3 meaningful objectives.
- Real input responsiveness.
- Real fail/retry loop.
- Real scoring or timing.
- Real progression.
- No autoplay pretending to be gameplay.
- No proof replay replacing user gameplay.
- No tiny loop tracks.
- No random primitive obstacle fields.
- No autoplay masquerading as a playable game.
- No “proof complete” status unless keyboard/mouse input visibly changes game state in captured evidence.

Racing acceptance criteria:

- Player can drive manually.
- Track is long enough and readable.
- Car starts on the track.
- Car remains visible.
- Camera is playable.
- Checkpoints/laps make sense.
- Start, mid-race, and finish screenshots look like a real racing prototype.

Platformer acceptance criteria:

- Character is readable and correctly scaled.
- Collision ledges match visual platforms.
- Route has coherent themed sections.
- Jumps are playable.
- The route is not a 10-second micro-demo.
- Camera tracks without hiding the player.
- Start, middle, and finish screenshots look coherent.

### Phase 7: Documentation Fixes

Update docs before rebuilding public examples. The docs must prevent future agents from repeating the same failure loop.

Required files to update or create:

- `README.md`
- `llms.txt`
- `AGENTS.md`
- `docs/project/plans/recovery-remediation-prd.md`
- `docs/agents/claims-and-boundaries.md`
- `docs/project/showcase/quality-gates.md`
- `docs/agents/asset-selection.md`
- `docs/agents/no-hackjob-rules.md`
- `docs/agents/game-example-standards.md`
- `docs/agents/rendering-proof-required.md`
- `docs/project/showcase-application-plan.md`

Documentation must say:

- Use typed assets from `src/aura-assets.ts`.
- Do not invent assets.
- Do not use raw GLB URLs.
- Do not use string asset IDs in safe public APIs.
- Do not use Three.js in public Aura3D examples.
- Do not use primitives as primary visuals for real objects, vehicles, characters, worlds, or games.
- Do not fake particles or renderer output with CSS/DOM/canvas.
- Do not claim PBR/HDR/WebGPU/postprocess/skinning/morphs/game production quality without route-specific browser evidence.
- Do not mark screenshots as acceptable if the primary subject is offscreen, hidden, oversized, unreadable, or ugly.
- Every showcase must include screenshot evidence and route diagnostics.

Documentation must also include:

- an explicit “audit first, examples second” workflow;
- file-level root-cause checklists for renderer, assets, camera, particles, and game runtime;
- examples of forbidden slop patterns and the correct Aura3D public API alternative;
- a clear rule that pretty screenshots are not optional evidence;
- a route-readiness checklist that blocks showcase launch until public APIs, diagnostics, and screenshots all agree.

### Phase 8: Rebuild Examples Only After Gates Pass

Only after Phases 1-7 pass, rebuild the examples.

Do not “polish” the current broken examples. Rebuild them from validated patterns. Example work starts only after a written gate report confirms Phases 1-7 are complete enough to proceed.

Each example must include:

- typed primary GLB assets
- asset quality grade
- no fake primary primitives
- no CSS scene effects
- screenshot evidence
- diagnostics evidence
- route-health evidence
- controls that work
- clear objective
- readable camera
- visual acceptance report

For the game examples:

- `showcase-turbo-drift-circuit` must become a real racing prototype, not a short route proof.
- `showcase-skyline-runner` must become a real side-scrolling platformer prototype, not a tiny primitive route.
- If the required quality cannot be reached, document the exact library gap blocking it and fix the library first.

The showcase rebuild must look materially different from the failed baseline. A route is not acceptable if it is still:

- a tiny 5-10 second micro-demo;
- mostly primitive boxes used as primary visuals;
- a GLB pasted onto mismatched primitives;
- badly cropped, hidden, floating, or unreadable;
- visually flat with unsupported PBR/high-res claims;
- a replay/autoplay proof instead of a playable route;
- a black or blank scene after load;
- a screenshot that cannot be explained as a coherent product/game/tool.

## Required Evidence Workflow

For every library fix and every example rebuild:

1. Run typecheck/build.
2. Launch the local dev server.
3. Use Playwright to load the route.
4. Simulate keyboard/mouse input where applicable.
5. Capture screenshots at multiple moments.
6. Inspect screenshots with `view_image`.
7. Collect console errors and diagnostics.
8. Save reports under `tests/reports/`.
9. Update `docs/project/plans/recovery-remediation-prd.md` with pass/fail status.

Do not end with “looks fixed” unless screenshots prove it.

For game routes, evidence must include at least:

- first-load screenshot;
- after-input screenshot;
- mid-route screenshot;
- failure or reset screenshot where relevant;
- finish/progression screenshot;
- input trace or deterministic replay that supplements, not replaces, manual input proof.

For rendering/asset routes, evidence must include at least:

- material/texture diagnostics;
- asset provenance and typed reference;
- camera/screen-bounds diagnostics;
- desktop screenshot;
- mobile or constrained viewport screenshot when the route is public.

## Required Final Output From The Recovery Pass

The final response must include:

- library files changed
- docs files changed
- validation apps created
- examples rebuilt
- tests run
- screenshot report paths
- known remaining gaps
- claims that are now proven
- claims that are still forbidden

Keep the final answer factual. Do not overclaim.

## Operating Principle

Aura3D should make it hard for developers and agents to create bad 3D output. If an example looks like primitive slop, the answer is not another example patch. The answer is to fix the engine, asset pipeline, docs, and quality gates until the public API leads developers toward credible 3D scenes by default.
