# Shadow PCF tap tiers (PRD-2 WP-3) on the 18,000-instance forest

Method: `tests/browser/shadow-filter-tier-ab.spec.ts` and `tests/browser/forest-10k.spec.ts` on the remote ACR runner (`tools/remote-acr/run.sh`, software WebGL2 / SwiftShader, 2 CPUs; not GPU timings). Forest = the bench forest (8,000 trunks + 8,000 canopies + 2,000 rocks, shadow, fog, 640x360), 44-frame plan, median of the last 12 frames. three.js 4x MSAA on the same plan: 1.43 s per frame, so the target "<= 2.5x" is **3.575 s per frame**. Raw results: `round1-dense-default-on/`, `round2-final-code/`.

## What was built

- `packages/rendering/src/shadows/ShadowFilterTier.ts`: tap tiers 32 / 16 / 8. A tier is a cap on the kernel length. A larger kernel is replaced by a Poisson-disk kernel of exactly `tier` taps whose RMS offset matches the source kernel; a kernel within the cap, or no tier, returns the same kernel object. Every way of lowering the tier is **opt-in**; with nothing requested the tier is 32 (reason `default`), which is a no-op for every kernel (the forward shader packs at most 32 taps). Opt-ins: an explicit tier, the quality-tier cap (low 8, medium 16, high and ultra 32), and the dense-caster cap (>= 8,192 casters, the auto-cascade cap threshold, takes 8 and never raises the quality cap).
- `ForwardShadowMapOptions.pcfTapTier` (ForwardPass.ts) is applied where the kernel is packed (`forward/Lighting.ts`): to the directional map in `applyForwardShadowMapUniforms`, and to the point-light and spot-light kernels in the same call (they take the directional map's tier; a scene with a point or spot shadow but no directional shadow map receives no tier). The shaders already loop over `u_shadowPcfSampleCount`, so `ShaderLibrary.ts` needed no change. The tier is applied before `packForwardShadowPcfSamples`, whose global limit stays 32; the packer does not know the tier, and does not need to, because a reduced kernel is built with exactly `tier` samples (unit-tested).
- Engine: `resolveShadowSystemConfig` resolves the tier into `ShadowSystemConfig.pcfTapTier` / `pcfTapReason`; `Prd02ShadowBridge` hands it to the forward shader (through `ShadowSystemConfigInput.pcfTapTier`, which the bridge reads). Controls: `?shadowtaps=32|16|8` or `__A3D_SHADOW_TAPS__` (explicit), `?qualitytaps=on` or `__A3D_QUALITY_SHADOW_TAPS__ = "on"` (quality-tier cap), `?densetaps=on` or `__A3D_DENSE_SHADOW_TAPS__ = "on"` (dense cap). The dense caster count the tier sees is the real count; the cascade kill switch `__A3D_DENSE_SHADOWS__ = "off"` only affects the cascade cap. Diagnostics: `globalThis.__A3D_SHADOW_TAP_TIER__ = { tier, reason, casterInstances, quality }` (same mechanism as `__A3D_DENSE_SHADOW_CAP__`).
- Not tiered: the legacy (non-flag) path. `renderer/ShadowOrchestration.ts` forwards only `filterKernel` and its options come from `Renderer.ts`, which this lane does not edit; a scene rendered through the legacy path never receives a tier whatever `?shadowtaps=` says. The flag-path `auto` quality resolves to `high` (desktop) or `medium` (coarse pointer), never `low`; `low` is reached only by a caller passing `tier: "low"` to `createPrd02ShadowOptions`.

**Target not met.** Best median 4.70 s against 3.575 s (3.29x against 2.5x). Moving the forest from the 9-tap kernel to the 8-tap tier changes the median by 0 to 2%, inside the 0.1 to 0.8 s run-to-run spread seen on this runner.

Likely cause (inferred, not isolated by a run): the forest's kernel is already small. The default (flag-path) bridge uploads a 3x3 grid (9 taps), so tier 8 removes one tap in nine. `evidence/forest-10k/README.md` records an earlier ablation (3 frames each, a different code state: 3.1 s without shadows, 4.1 s with, so about 1.2 s for shadow sampling in the camera pass). If that figure holds for the final code, one ninth of it is about 0.13 s, which is consistent with the measured 0 to 2% change. No run isolated the shadow-sampling cost of the final code, and none measured the 9 -> 8 saving by itself; the 0.13 s is arithmetic on the older ablation. Meeting 3.575 s would take about 1.2 s out of 4.7 s, i.e. removing essentially all shadow lookups, which no 8-tap tier does. The remaining floor reported in `evidence/forest-10k/README.md` is the fragment-bound camera pass (about 2.7 s with no shadows), not the tap count.

Timing rows were taken before the review fixes below. The fixes change no code path at quality `high` (the forest's tier), so they do not move these numbers; they were not re-timed.

**The forest is the only scene that measures a tier effect, and it fails the limit**: mean difference is far inside 2/255, but the largest single-pixel difference at shadow penumbrae is 9/255 (silhouettes 19/255), over the 6/255 limit. The silt row sits inside its own capture-to-capture noise and the large-scene row is insensitive to the tier, so neither confirms nor refutes that, and neither is a pass. There is no usable visual evidence on the showcase games the WP names: examples/roadster-hours-port, examples/ninja-runner-port and apps/aura-clash-showcase animate, and two captures of the same configuration already differ by up to mean 21.9 / interior 135 (ninja-runner) and mean 0.43 (roadster), so the noise floor swamps any tier effect; examples/drift-and-deliver-port, apps/showcase-vault-breakers and apps/showcase-smart-city-control never resolve a flag-path shadow config (`__A3D_SHADOW_TAP_TIER__` unset), so the tier cannot reach them (their frames were identical across all configurations, which says nothing about a tier effect).

## Decision

The 8-tap tier buys nothing measurable on the forest and exceeds the 6/255 pixel limit at penumbrae, so per the WP it **stays opt-in**. After the review fixes below, a render that asks for nothing resolves tier 32 (reason `default`), a no-op for every kernel: this holds for every quality tier, because the quality-tier cap (low 8, medium 16) is now its own opt-in (`?qualitytaps=on`) instead of a default. Before the fix, quality `low` mapped to 8 by default, which swapped the 9-tap bridge grid for an 8-tap Poisson kernel on every `low` render; that was a defect, not a documented behaviour. Tiers 16 and 32 never change a 9-tap kernel, so `low` was the only quality tier that changed output. The dense-caster cap (`?densetaps=on`), the quality-tier cap (`?qualitytaps=on`) and the explicit tier (`?shadowtaps=`) remain for authors who want the cheaper kernel.

What backs "defaults unchanged": unit tests (`tests/unit/rendering/shadow-filter-tier.test.ts`: every quality tier resolves `default`/32 and the resulting kernel is the same object as the authored one; dense scenes at `low` stay at 32 without an opt-in) and the remote run `medium-default` (below). No browser run exercises quality `low`: the flag-path `auto` quality never resolves `low`, so no example page reaches it; `low` is covered by the unit tests only. `quality: "production"` byte-identity is likewise covered by the kernel-identity unit tests plus the forest and large-scene captures at `high` (default vs pinned 32: diff 0), not by a captured `production` render at every quality tier.

Not done, and why: a larger saving needs fewer than 8 taps or a hardware-compare single-tap path for dense casters (the forest's camera pass is fragment-bound), which is outside the 32 / 16 / 8 tiers specified here.

## Review fixes (round 3: `round3-review-fixes/`)

A review of the first commit found four defects and several claims the evidence did not back. What was checked and changed:

- **Quality-tier default changed output (real, fixed).** `resolveShadowPcfTapTier` mapped quality `low` to 8 taps by default, replacing the 9-tap bridge grid with an 8-tap Poisson kernel; the forest A/B measures exactly that swap at up to 9/255 interior and 19/255 silhouette, over the 6/255 limit. The quality-tier cap is now opt-in (`qualityDefault`, engine `?qualitytaps=on`); the dense cap is a strict opt-in (`denseDefault === true`). The old unit test that asserted low -> 8 as the default is replaced by tests asserting every quality tier resolves 32 / `default` and returns the authored kernel object, plus opt-in tests for the mapping. One correction to the review: the flag-path `auto` quality resolves to `high` or `medium` and never `low`, so `low` is reached only through an explicit `tier: "low"`; the defect is real for those callers.
- **Point and spot kernels not tiered (real, fixed; legacy path not fixed).** `applyForwardPointShadowMapUniforms` and `applyForwardSpotShadowMapUniforms` now apply the directional map's tier (unit-tested at 32/16/8 and without a tier). The legacy path (`ShadowOrchestration.ts`, options from `Renderer.ts`) still gets no tier; `Renderer.ts` belongs to another lane, so this is recorded here instead of changed. The review's "`ShadowSystemConfigInput.pcfTapTier` is never read" is not correct: `Prd02ShadowBridge.bridgeShadowMap` reads it (`tsc` fails when the field is removed), so it stays. The claim that the validator should enforce the tier is not a defect: `packForwardShadowPcfSamples` enforces the global 32-tap limit and the tier is applied before it, building kernels of exactly `tier` samples (unit-tested).
- **Dense tap tier coupled to the cascade kill switch (real, fixed).** `__A3D_DENSE_SHADOWS__ = "off"` no longer zeroes the caster count the tap tier and `__A3D_SHADOW_TAP_TIER__.casterInstances` see; it still disables only the cascade cap. Unit-tested (18,000-instance scene with the switch off reports 18,000 and tier 8 when the dense tap opt-in is on, and 32 when it is off).
- **Large-scene row (real, fixed in text).** The row is an insensitive scene, not a pass; see the visual table above.
- **Acceptance "dense casters (>= 8,192) default to the lower tier" is partly met, not met.** Dense scenes get the lower tier only with `?densetaps=on`; by default they keep the authored kernel, because the lower tier fails the visual limit on the forest.
- **"Byte-identical" claims.** Now backed by: unit tests across all four quality tiers; remote forest at `high` (default vs pinned 32: diff 0, tier `default`/32 for 18,000 casters), large scene at `high` (diff 0); and a new remote check `medium default unchanged` (coarse-pointer context, `quality: "medium"`, 18,000 casters: default vs pinned 32 diff 0, mean/interior/over6/edge all 0; `round3-review-fixes/shadowtier-medium-default.json`). Quality `low` has no browser run (no page reaches it), only unit coverage.
- **Re-run in this round:** `vitest` on `shadow-filter-tier.test.ts` (16 tests), `shadow-family-b1`, `shadow-pass`, `shadow-projection`, `shadow-pcf-slope-bias`, `dense-shadow-cascades` and `production-bridge-boundary`: 65 passed. `tsc -p tsconfig.check.json`: 59 errors, none in the changed files (all in unrelated tests and tools that this change does not touch; I did not run tsc on the base commit). `tests/unit/{rendering,engine,agent-api}`: 55 failures with the changes and 55 with the changes reverted (same 18 files; `probe-half-float-equivalence.test.ts` failed once in one run and passed alone, a timing flake). Remote: `visual group 1` and `medium default unchanged` passed on the ACR runner (run `wp3fix1`, image tag deleted). The review also named `fog-forward-absorption`, which does not exist in this tree; the failing `environment-lighting-reflection-platform` test throws `createNamedEnvironmentPreset was removed by PRD-10` and does not touch shadows.
- **Not re-run:** the forest timing rows (taken before these fixes; the fixes change no code path at `high`). Groups 2 and 3 of the visual audit (unusable scenes, unchanged by the fixes).
