  ## Three uncovered items, one real bug

  grep for race/parallel/concurrent in the freshness suite returned nothing — yet "parallel tests cannot race shared artifacts" is defect 71's exact root cause. Two other listed items were also uncovered: screenshot-SHA mismatch as its own cause,
  and explain-staleness naming the exact mismatch.

  The bug: writeArtifactAtomically named its temp file ${path}.${pid}.${Date.now()}.tmp. That is not unique — measured, 200 rapid calls in one process produce 1–2 distinct names, since Date.now() is millisecond-resolution and the pid is constant.

  I demonstrated the consequence directly: with a shared temp path, the second writeFileSync destroys the first writer's staged bytes before it renames, so one artifact silently becomes the other's content while both calls report success. That is
  precisely the fault this module exists to prevent — output that looks written and is wrong — reintroduced by the writer meant to prevent it.

  Fixed with a monotonic counter plus random suffix: the counter guarantees uniqueness within a process even if the RNG repeats, the random bytes across processes. Measured after: 5000/5000 unique.

  ## 7 tests added (40 in that file)

  The ones carrying weight:

  - 24 concurrent writers with differently-sized payloads must leave one writer's complete output — verified by checking the filler length matches that writer's own index, so an interleaved write fails an internal-consistency check rather than
    merely looking odd

  - A behavioural guard on the naming scheme itself, asserting the retired Date.now()-keyed form cannot return. I added this because the concurrency tests can pass by luck under synchronous serialization; this pins the property that makes them
    pass, not just the outcome

  - Screenshot-digest mismatch as its own cause: unchanged file reads fresh, a file rewritten by a different producer reads stale and is named — the exact Aura Clash shape, where one artifact was rewritten with everything else untouched
  - explain-staleness naming each mismatch with both digests, and not reporting unchanged dependencies so the signal isn't diluted

  ## Honest scope note

  Node's writeFileSync/renameSync are synchronous, so writers in a single process serialize regardless. The collision mattered for genuinely parallel writers — separate processes, worker threads — and any future async path. The fix removes the
  hazard rather than relying on the current execution model to hide it.
