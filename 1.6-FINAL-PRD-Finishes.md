## 0. Executive truth

Aura3D 1.6 has completed substantial architecture, packaging, bundle-entry,
typed-asset, evidence, and shared-runtime work. It has **not** yet demonstrated
that Aura3D is a direct, current, head-to-head competitor to the real Three.js
ecosystem.

The existing four release-candidate screenshots do not show a material visual
change from their earlier state. Their automated evidence proves freshness,
boot, drawing, typed assets, interaction, and route integrity. It does not prove
a materially better product or a compelling reason to choose Aura3D.

The current comparison is also frozen against `three@0.165.0`, while the current
npm release observed on 2026-08-08 is `three@0.185.1`. Modern Three.js includes a
substantially evolved `WebGPURenderer`, WebGL2 fallback, TSL/node materials, and
node-based postprocessing. A comparison against 0.165.0 is historical evidence,
not a current competitive verdict.

This PRD finishes the work by requiring five outcomes together:

1. **Current competition:** compare against the latest stable Three.js and the
   real stack developers use around it.
2. **Intentional ownership:** Aura3D owns only its renderer/core and its genuine
   platform differentiation; commodity subsystems use mature external engines,
   become optional integrations, or are removed.
3. **Public depth:** the safe public API reaches the production renderer and the
   capabilities used in head-to-head examples.
4. **Material examples:** flagship routes become visibly and interactively
   better, with before/after proof that survives removal of HUD and text.
5. **Defensible release:** no broad claim, version, publication, or deployment
   occurs until the current comparison, package, visual, and external-consumer
   gates all pass.

Passing tests is necessary. It is not the product outcome. A release candidate
that looks the same, compares against an obsolete baseline, or hides major
capabilities behind internal packages is not complete.

## 2. Definition of “direct, current, head-to-head competitor”

Aura3D may use this description only when all five layers below pass.

### 2.1 Current baseline

- The baseline is the latest stable Three.js release available when the final
  benchmark lock is created, not the version already present in the lockfile.
- As observed on 2026-08-08, that baseline is `three@0.185.1`; execution must
  re-query npm and record the exact version, integrity, release date, and commit.
- If the baseline changes after implementation begins, freeze it for that run,
  document the newer release, and perform a delta review before publication.
- A baseline more than two stable Three.js releases behind at publication must
  be rerun or explicitly described as historical. It cannot support “current.”

### 2.2 Real ecosystem stack

The comparison is not against bare Three.js where real developers normally add
other tools. Each workload must name and lock its actual baseline stack:

- Three.js core and official addons;
- `WebGLRenderer` and `WebGPURenderer` where applicable;
- TSL/node materials for modern WebGPU/custom-material workloads;
- official loaders and postprocessing;
- React Three Fiber and drei for React workflows when those represent the common
  alternative;
- Rapier or another mature physics engine for physical game workloads;
- Recast/Detour or another mature navigation library for navmesh workloads;
- a maintained audio library or the browser Web Audio API for audio workloads;
- glTF Transform, Draco, Meshopt, KTX2/Basis, and other established asset tools
  where they are the real baseline.

No Aura3D win may be produced by comparing an integrated Aura3D workflow against
an intentionally incomplete Three.js setup.

### 2.3 Five separate verdicts

The aggregate comparison must report these separately:

1. **Renderer correctness and visual quality**
2. **Renderer/API feature depth**
3. **Developer workflow and authored complexity**
4. **Application-platform integration and evidence**
5. **Ecosystem breadth, escape hatches, maintenance, and adoption risk**

Aura3D may win workflow or integration while losing renderer breadth. The report
must say so. No weighted aggregate may hide a category loss.

### 2.4 Minimum market-credible outcome

- [ ] Zero high-priority current-baseline gaps in the selected public target.
- [ ] Zero `parity-unproven` rows in any capability advertised on the homepage,
      README, npm package, or flagship example.
- [ ] Every `exceed` row has a public API, production consumer, current browser
      evidence, current competing implementation, and reproducible protocol.
- [ ] Aura3D has at least three material workflow wins and at least three
      renderer/output parity results against the current baseline.
- [ ] Aura3D loses no required workload on correctness, crash rate, resource
      lifecycle, or browser compatibility.
- [ ] Any performance loss is disclosed per workload and remains inside a
      predeclared non-inferiority margin.
- [ ] Ecosystem breadth is reported honestly; it is never converted to “parity”
      from a short selected inventory.

## 3. Binding execution rules

### F1 — Current evidence only

No release claim may rely on an artifact generated before the code, dependency
lock, asset, browser, GPU configuration, or comparison baseline it claims to
measure.

### F2 — Public production-path lineage

Evidence must execute a documented public package entry. Deep source imports,
test-only shims, route-local replicas, Canvas2D stand-ins, metadata-only claims,
and decorative imports prove nothing about the public product.

### F3 — No threshold laundering

Do not loosen a bundle, visual, behavior, performance, freshness, accessibility,
or quality threshold to make a failing implementation pass. If a threshold is
wrong, demonstrate that with calibration cases and record the change separately.

### F4 — Fix the lowest correct owner

Shared defects are fixed in the owning package. No route-name conditional,
route-local renderer, copied physics integrator, copied input loop, or fixture
boolean may substitute for a library fix.

### F5 — Own differentiation, integrate commodities

Aura3D owns:

- renderer/device abstraction and production rendering pipeline;
- scene graph and typed scene authoring;
- asset intelligence, provenance, admission, and typed asset generation;
- agent-oriented application composition;
- templates and scaffolding;
- route health, interaction audit, diagnostics, and evidence freshness;
- migration and compatibility surfaces that materially reduce adoption cost.

Commodity capabilities must use a mature external implementation, be a thin
adapter over a browser standard, be optional, or be removed. A custom commodity
implementation needs a new accepted ADR proving an external option cannot meet
the required contract.

### F6 — One owner per capability

Adapters are allowed. Two live implementations are not. Source architecture
tests must reject a second solver, controller, navigation engine, audio engine,
input listener owner, animation integrator, or renderer path.

### F7 — No blanket deletion

“Remove the subsystem” never means deleting public or generated dependencies
blindly. Before removal, produce R8-style evidence for:

1. runtime consumers;
2. dynamic/generated consumers;
3. public exports;
4. CLI discovery;
5. docs generators;
6. retained schemas/reports;
7. downstream package contracts;
8. migration impact.

If a public subsystem must disappear, use deprecation and a major-version plan.

### F8 — Heavy systems are optional

Physical simulation, navmesh generation, editor tooling, video encoding, and
other heavy capabilities must not enter the cube or product-viewer critical path.
Use optional packages, dynamic imports, workers, or offline pipelines.

### F9 — Real visuals, not UI evidence

DOM/CSS/canvas overlays are UI. They cannot prove particles, lighting, labels,
shadows, reflections, trails, explosions, materials, scene text, or renderer
effects.

### F10 — Material improvement is mandatory

A flagship route is not rebuilt merely because it boots or its screenshot hash
changes. The improvement must remain visible after masking text, HUD, and chrome.

### F11 — Independent human review stays downward-only

Automated checks may block a human approval. They may never create one. Human
approval must name the reviewer, exact commit, route hashes, screenshots, and
scope.

### F12 — Current Three.js is a moving target

Re-query the stable version immediately before the final two serial comparison
runs. Record any changes in renderer, TSL, addons, loaders, examples, or public
API that affect the locked workloads.

### F13 — No broad superiority score

Publish per-workload results. Do not collapse incomparable dimensions into a
single marketing score.

### F14 — No compatibility fiction

Preserve valuable concepts, not broken semantics. Every intentional removal or
behavior change has a before/after migration entry and installed-package test.

### F15 — One workstream per commit

Each subsystem replacement, renderer feature, example rebuild, comparison
fixture, documentation update, version decision, and release action is committed
separately and reviewably. Never use `git add .`.

### F16 — No secret exposure

Use configured authentication. Never print, inspect, serialize, pass in command
arguments, commit, package, deploy, or include credentials in evidence.

### F17 — Generated boundaries

Do not hand-edit `dist/`, generated asset maps, reports, screenshots, coverage,
release artifacts, route-health output, or generated comparison Markdown.

### F18 — Clean external consumers

Every public claim must survive an isolated install outside the monorepo with no
workspace aliases, symlinks, private imports, local absolute paths, or source
fallbacks.

### F19 — Breaking architecture may require a major version

The filename says 1.6, but the release version is evidence-driven. If public
packages, working exports, or common semantics are removed without compatible
adapters, the correct release is 2.0.0. Do not force breaking work into 1.6.0.

### F20 — Release is an external state

“Complete” requires verified npm packages, tag, GitHub release, production site,
registry install, live routes, and clean final tree. Local green tests are not a
release.

## 5. Phase 1 — Subsystem ownership and external-integration audit

Create `docs/architecture/final-subsystem-ownership.md` and a generated machine
report covering every package and runtime subsystem.

### 5.1 Required classification

Every subsystem receives exactly one disposition:

- `AURA-CORE` — must remain Aura3D-owned to compete;
- `AURA-MOAT` — differentiated platform capability;
- `EXTERNAL-ADAPTER` — public Aura3D contract over a mature dependency;
- `BROWSER-STANDARD` — thin wrapper over a browser API;
- `OPTIONAL-PLUGIN` — separately installed/lazy capability;
- `COMPATIBILITY-ONLY` — retained for migration, not recommended for new apps;
- `DEPRECATE-REMOVE` — migration window and next-major removal;
- `DELETE-NOW` — zero-consumer, non-public, R8-cleared source;
- `EVIDENCE-ONLY` — test/tool fixture that cannot ship as capability.

- [ ] Same assets and asset hashes.
- [ ] Same camera projection/pose and framing target.
- [ ] Same canvas, DPR, viewport, and browser.
- [ ] Same lighting intent, environment, tone mapping, and exposure.
- [ ] Same animation clip/time and deterministic input trace.
- [ ] Same warmup, sample count, session count, cache state, and machine.
- [ ] Baseline stack is implemented idiomatically, not deliberately verbose.
- [ ] Aura3D uses only public installed packages.
- [ ] Three.js uses official/current public packages and realistic addons.
- [ ] Neutral harness code is shared or reported separately.

### WS-4.3 Required measurements

Per workload retain raw samples and report:

- install and scaffold time;
- authored application lines excluding generated assets/config;
- dependency count and lockfile size;
- production JS/WASM/assets gzip and brotli;
- parse/compile/init time;
- first valid frame;
- CPU frame time, GPU timer when supported, wall-clock cadence, variance;
- draw calls, triangles, textures, buffers, render targets, memory where valid;
- screenshot structural metrics and human side-by-side review;
- interaction correctness;
- console/runtime/network failures;
- resource lifecycle after repeated reload/dispose;
- accessibility and input coverage;
- deployment complexity;
- escape-hatch complexity;
- unsupported or unproven capabilities.

### WS-4.4 Verdict rules

- [ ] Correctness failures cannot be offset by fewer lines or smaller bundles.
- [ ] Visual-quality failures cannot be offset by faster blank frames.
- [ ] Performance claims require real engine paths and separate CPU/GPU/wall
      taxonomy.
- [ ] A non-inferiority threshold is declared before results are produced.
- [ ] Every win/loss includes magnitude, variance, environment, and scope.
- [ ] The aggregate emits `wins`, `parity`, `losses`, `unproven`, and `not
      comparable`, never a universal score.
- [ ] Independent rerun instructions work from a clean checkout.

### WS-4.5 External replication

- [ ] Run the comparison from packed/installed Aura3D packages, not workspace
      source.
- [ ] Run at least one clean machine or clean VM profile.
- [ ] Retain the exact context bundle and artifact hashes.
- [ ] Have an independent human inspect the final same-scene gallery.

## 10. Phase 6 — Developer experience and package architecture

### WS-6.1 Recommended package topology

The final topology should approximate:

```text
@aura3d/engine                  compatibility surface
@aura3d/engine/lean             scene + production renderer
@aura3d/engine/lean-product     lean + typed glTF product path
@aura3d/engine/lean-game        lean + deterministic arcade/input services
@aura3d/physics-rapier          optional physical simulation, if selected
@aura3d/navigation-recast       optional navigation/crowd, if selected
@aura3d/audio                   one selected thin audio adapter
@aura3d/three-compat            isolated migration surface
@aura3d/editor                  optional authoring application
@aura3d/media-node              Node-only encoding/publishing
```

Exact names require package/export analysis and may change. The properties may
not:

- core and product do not pay for physics/navigation/editor/media;
- game arcade does not silently claim physical simulation;
- browser packages have no Node-only transitive edge;
- optional WASM is lazy/separate;
- compatibility is isolated;
- one capability has one owner.
