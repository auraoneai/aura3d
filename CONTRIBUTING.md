# Contributing Guide

Version: 2.0.3

Public claims and release wording are governed by `docs/project/product-studio-claim-registry.md`.

## Scope

Contributions must preserve the current governance rules:

- keep implementation edits scoped to the owning package or tool;
- do not revert unrelated work from other agents or contributors;
- add focused tests for behavior changes;
- update source checkboxes only after the relevant command passes;
- keep public claims aligned with `docs/agents/claims-and-boundaries.md`,
  `docs/project/claim-guidelines.md`, and the relevant route evidence.

## Showcase And Example Integrity

Release-facing examples must prove the Aura3D path they claim. A PR is not
ready when a route only boots, or when the main subject is a primitive stand-in
for something the prompt named as a real object, character, vehicle, world, or
product.

For showcase, template, or example PRs:

- resolve real GLB/glTF assets through the Aura3D CLI;
- import generated typed refs from `src/aura-assets.ts`;
- use `model(assets.x)`, not `model("x")`, raw URLs, or invented IDs;
- do not import `three`, `GLTFLoader`, or renderer internals in public examples;
- keep CSS/DOM to UI chrome, not scene particles, 3D effects, scanlines, or
  fake animation;
- include route-health evidence and desktop/mobile screenshots;
- include keyboard/input evidence for games;
- label unsupported renderer features as prototype, internal, or planned.

## Local Verification

Run the smallest relevant command first, then broader gates when appropriate:

```sh
pnpm typecheck
pnpm test:unit
pnpm test:integration
pnpm verify:claims
pnpm verify:release
```

For asset-backed public examples, run:

```sh
pnpm exec aura3d assets validate --source --release
```

For governance-only changes, run the governance unit tests and claim scan:

```sh
pnpm exec vitest run tests/unit/tools/governance-docs.test.ts
pnpm verify:claims
```

## Pull Request Checklist

- Describe the changed paths and owning workstream.
- List commands run and whether each passed or failed.
- Link report JSON files generated by the change.
- Link route-health output when a route changed.
- Link desktop and mobile screenshot evidence when visuals changed.
- Link game input or deterministic replay evidence when gameplay changed.
- Confirm `assets validate --source --release` passed for public examples.
- Confirm every primary character, vehicle, product, world, or environment is a
  typed asset or the route is explicitly abstract/prototype.
- Explain any remaining blockers.
- Do not use stronger public claim language than
  `docs/agents/claims-and-boundaries.md` and `docs/project/claim-guidelines.md`
  permit.

## Issue Templates

Use `.github/ISSUE_TEMPLATE/bug_report.yml` for defects and `.github/ISSUE_TEMPLATE/feature_request.yml` for enhancements.


## Good First Issues

Good first contributions include:

- improving agent docs, prompt recipes, and typed asset examples;
- adding Vite template documentation for browser 3D apps;
- tightening comparison wording while preserving claim boundaries;
- adding screenshot or route-health evidence to examples;
- improving troubleshooting docs for blank canvas, missing GLB/glTF assets, Vite deploy paths, and screenshot failures.

## Docs And Example PRs

For docs or example pull requests, include:

- the source prompt or use case;
- asset source and license when a GLB/glTF file is involved;
- commands run and whether each passed or failed;
- screenshot path or route-health evidence when visuals changed;
- any claim boundary that applies, especially for manual renderer code
  comparisons, WebGPU, PBR, skinned animation, game-runtime, or benchmark
  wording.

## Issue Reports

When filing an issue, include package version, template or route, prompt, asset source, commands run, runtime error, route-health output, screenshot evidence, and deployment target when relevant.
